## 0. Framing: from learning a policy to computing one

Week 1 ([`week1-study-notes.md`](./week1-study-notes.md)) built controllers entirely from data: behavioral cloning (BC) fits a policy function `π_θ(o) → a` directly to an expert's recorded (observation, action) pairs, with no explicit model of how the robot's physics works. DAgger patched BC's error-compounding problem by *interactively querying* an expert, again with zero physics modeling — the controller is purely a function fit to examples.

This week takes the opposite starting point. Instead of imitating an expert's actions, **optimal control** starts from two ingredients specified up front: a **cost function** describing what "good" behavior means numerically (e.g. "end up near the target, don't use much force"), and a **dynamics model** describing how the robot's state evolves in response to actions. Given these two ingredients, the actions are not learned from demonstrations at all — they are *computed*, by an optimization procedure that searches for the action sequence minimizing total cost under the model.

Same end goal as Week 1 — get a robot to do something useful — completely different machinery:

| | Behavioral cloning (Week 1) | Optimal control (this week) |
|---|---|---|
| What's given | Expert demonstrations (observation, action) pairs | A cost function + a dynamics model |
| What's learned/computed | A policy function fit by gradient descent | An action sequence found by optimization |
| Physics model | None — implicit in the data | Explicit — `x_{t+1} = f(x_t, u_t)` |
| Needs an expert? | Yes | No |

This sets up the first of four recurring framing questions this week's synthesis (§9) answers in full: **how do optimal-control methods compare to learning-based methods, and what's their value?** The short preview: optimal control needs no demonstration data and comes with strong mathematical guarantees for the special cases it can solve exactly, but it needs an accurate model and a hand-specified cost — exactly the two things BC never needs. The two approaches turn out to be far more complementary than competing, as §9.1 develops in full once the machinery to see why is on the table.

## 1. Vocabulary bridge: Bellman equations unify control theory and RL

Optimal control and reinforcement learning (RL) grew up in different academic communities — control theory in engineering departments since the 1950s, RL in computer science/AI since the 1980s — and as a result use different words for what turn out to be almost the same mathematical objects. This section builds the shared vocabulary from scratch, since the rest of the week (and this course's later RL content) freely swaps between the two dialects.

**State.** The **[state](https://en.wikipedia.org/wiki/State_variable)** `x_t` (control theory's usual letter) or `s_t` (RL's usual letter) is a full description of the system at time `t` — everything needed, together with the current action, to determine what happens next. For a robot arm this might be joint angles and joint velocities; Week 1 called this the same thing (state/observation) when introducing the MDP.

**Dynamics / transition.** The **dynamics** (control theory's term) or **[transition function](https://en.wikipedia.org/wiki/Markov_decision_process)** (RL's term) describes how the state evolves: `x_{t+1} = f(x_t, u_t)` in the deterministic case, or a conditional distribution `p(x_{t+1} | x_t, u_t)` in the stochastic case. Control theory almost always writes the action as `u_t` (from the German *Steuerung*, "control/steering," reflecting the field's European roots) rather than RL's `a_t` — same object, different letter. This course will use `x` and `u` in control-theoretic sections (this week) and `s`/`a` when discussing RL algorithms directly, translating between them as needed.

**Cost vs. reward — the same overloaded idea, sign-flipped.** Control theory scores a trajectory with a **cost** `c(x_t, u_t)` to be *minimized* (small is good); RL scores it with a **reward** `r(x_t, u_t)` to be *maximized* (large is good). These are the literal negatives of each other (`c = -r`) and nothing more is meant by using one or the other — this course will flag every time "cost" and "reward" appear in the same discussion so as not to silently swap sign conventions.

**Disturbance / noise term.** Real dynamics are rarely perfectly known or perfectly deterministic — actuators slip, sensors are noisy, surfaces have unmodeled friction. This is captured by adding a **disturbance** or **noise term** `e_t` (or `w_t`) to the dynamics: `x_{t+1} = f(x_t, u_t, e_t)`, usually with `e_t` drawn independently at each step from some known or assumed distribution (often Gaussian). §2.3 shows the special, exactly-solvable case where this noise term is Gaussian and the dynamics are otherwise linear (called **LQG**).

**Horizon.** As in Week 1, the **horizon** `T` (or `N`) is the number of decision steps in one rollout. A **finite-horizon** problem plans for a fixed number of steps ending at a known time `T`; an **infinite-horizon** problem plans forever, which requires the cost to be structured so an infinite sum doesn't blow up (e.g. weighting future costs by a discount factor `γ < 1`, exactly RL's usual discounting).

**Disambiguating "policy" — this week's most important overloaded term.** Week 1 used "policy" loosely for "the function that decides what to do." This week forces a precise split between two genuinely different mathematical objects that will both be called "policy" throughout the literature:

- **Control theory's policy-as-control-law**: a deterministic function of state and time, `u_t = π_t(x_t)`, that on every use outputs one specific action. LQR (§2) computes exactly this kind of object — a different linear function `π_t` for each timestep.
- **RL's policy-as-a-distribution**: `π_θ(a_t | x_t)`, a full probability distribution over actions given the state, from which an action is *sampled*. Week 1's BC and DAgger policies were technically control laws in this sense (deterministic regression outputs) except where §7's energy-based or diffusion policies made them explicitly distributional.

Every time "policy" appears below in a context where the distinction matters, these notes will say "control law" or "distribution" explicitly rather than leaving "policy" to carry both meanings silently — exactly the kind of overloaded-term trap the project's writing conventions call out.

### 1.1 The Bellman equation: recursion via "optimal substructure"

The central mathematical tool tying this whole week together is named after **[Richard Bellman](https://en.wikipedia.org/wiki/Richard_E._Bellman)**, who developed **[dynamic programming](https://en.wikipedia.org/wiki/Dynamic_programming)** in the 1950s specifically to solve multi-stage decision problems like this one. His **principle of optimality** — the idea this section builds up from scratch — says, informally: *whatever the optimal decision was at step 1, the remaining decisions from step 2 onward must themselves be optimal for the sub-problem that remains.* An optimal plan can't contain a suboptimal sub-plan anywhere inside it, because you could always swap in a better sub-plan without affecting anything that happened before it.

> **Plain-language analogy.** Planning a road trip to minimize total driving time: if the fastest full route happens to pass through Chicago partway through, then the remainder of that route (Chicago to the final destination) must *itself* be the fastest possible route from Chicago onward — if a faster Chicago-to-destination route existed, splicing it in would make the whole trip faster, contradicting that the original route was already the fastest. This "the tail of an optimal plan is itself optimal" property is exactly optimal substructure.

This suggests solving the problem **backwards**: figure out the optimal decision for the *last* step first (trivial — there's no future left to worry about), then the second-to-last step (given that you'll act optimally on the last step), and so on back to the first step. Define the **cost-to-go** (control theory's name) or **value function** (RL's name) — two names for the exact same recursively-defined quantity — as the minimum possible total future cost achievable starting from a given state at a given time:

```
J*_t(x) = minimum total cost incurred from time t onward, starting at state x, acting optimally
```

**Why "cost-to-go"?** The name is literal: it's the cost still to be paid *going forward* from this point on — not the cost already spent getting here (that's sunk and irrelevant to what to do next). RL's synonym, **value function**, frames the identical quantity positively (how much future reward is this state worth) rather than as a cost to be minimized, but the recursive structure is identical either way.

The **[Bellman equation](https://en.wikipedia.org/wiki/Bellman_equation)** is the recursive relationship the optimal-substructure argument implies: the optimal cost-to-go at time `t`, from state `x_t`, equals the cost of whatever action is taken *right now*, plus the optimal cost-to-go from wherever that action leads, minimized over the current action:

```
J*_t(x_t) = min_u [ c(x_t, u_t) + E[ J*_{t+1}( f(x_t, u_t, e_t) ) ] ]
```

The expectation `E[·]` is needed only because the disturbance `e_t` makes the next state random; in the deterministic case it can be dropped. Read right-to-left, this equation says nothing more than the optimal-substructure principle above: *the best you can do from here is pay whatever the current step costs, then act optimally from wherever you land.*

> **Worked numeric example.** Consider a robot on a 1-D line of positions `{0, 1, 2}` that must reach position 2 within `T = 2` steps (decisions at `t = 0` and `t = 1`, then the episode ends at `t = 2`). Actions are "stay" (cost 2) or "move +1" (cost 1); moving past position 2 is not allowed (treat as staying). The terminal cost at `t = 2` is a penalty of 10 for not being at the goal, 0 for being at it.
>
> Backward pass, one timestep at a time: at `t = 2` there are no more decisions, so `J*_2(x)` is purely the terminal penalty: `J*_2(2) = 0`, `J*_2(1) = 10`, `J*_2(0) = 10`. At `t = 1`, apply the Bellman equation using these already-solved `t = 2` values: from `x = 1`, staying costs `2 + J*_2(1) = 12` while moving to `2` costs `1 + J*_2(2) = 1` — moving wins, so `J*_1(1) = 1`. From `x = 0`, staying costs `2 + J*_2(0) = 12` while moving to `1` costs `1 + J*_2(1) = 11` — moving wins again, so `J*_1(0) = 11`. Finally at `t = 0`, from `x = 0`: staying costs `2 + J*_1(0) = 13`, moving to `1` costs `1 + J*_1(1) = 2` — moving wins, `J*_0(0) = 2`. The optimal plan (move, move) falls straight out of which action won at each step, and every number was computed exactly once by reusing the already-solved value one step later — never recomputed by re-exploring the future from scratch. That reuse of already-solved sub-answers is exactly what makes dynamic programming efficient, and exactly what the optimal-substructure argument above guarantees is valid.

Two further pieces of standard notation, both counting the *same* recursively-defined optimal cost-to-go / value under different names depending on whether a fixed control law or the best-possible one is being scored:

- **`V*(x)`** — RL's name for the optimal value function, i.e. `J*(x)` under RL's positive-reward sign convention (infinite-horizon or time-independent version of `J*_t`).
- **`Q*(x, a) = r(x, a) + γ · E[V*(x')]`** — the optimal **action-value function**: the value of taking a *specific* action `a` right now (not necessarily the optimal one) and acting optimally forever after. `V*(x) = max_a Q*(x, a)` — the value function is just the action-value function maximized over the current action.
- **`V^π(x)`, `Q^π(x, a)`** — the same two quantities, but evaluated under a *fixed*, possibly suboptimal control law/distribution `π`, rather than the optimal one. These measure "how good is this specific policy," as opposed to `V*`/`Q*`'s "how good is it possible to be at all."

§2 shows the one broad case where this backward recursion can be solved **exactly, in closed form, with pure linear algebra** — no numerical optimization at any step — and why that's possible.

## 2. LQR: the fully solvable special case

### 2.1 Why start with a toy case

The Bellman recursion of §1 is a *general* recipe — it applies to any dynamics and any cost — but "minimize over `u_t`" at each backward step is, in general, an arbitrary, possibly nasty nonlinear optimization problem that has to be solved numerically, separately, at every single state and timestep. That's completely impractical for continuous state/action spaces (there are infinitely many states to solve it at).

There is exactly one broad, useful special case where the minimization in the Bellman equation can be solved once, symbolically, with calculus, rather than repeatedly, numerically: when the dynamics are **linear** and the cost is **quadratic**. A quadratic function of a single variable is a parabola — a bowl with one global minimum, no local minima to get stuck in, found by simple calculus (`derivative = 0`). A quadratic function of a vector, `x^T Q x`, is the multivariable generalization of that same bowl shape (as long as `Q` is **[positive-definite](https://en.wikipedia.org/wiki/Definite_matrix)** — see below): still one global minimum, still findable by setting a gradient to zero and solving a linear system. This is the entire reason this special case is worth an entire subsection of derivation: the Bellman minimization becomes freshman calculus instead of general nonlinear optimization.

This special case is called the **[Linear-Quadratic Regulator (LQR)](https://en.wikipedia.org/wiki/Linear-quadratic_regulator)** — and the name is worth unpacking term by term, since every word is doing real work:

- **Linear** describes the *dynamics*: `x_{t+1} = A x_t + B u_t`, where `A` and `B` are fixed matrices (no `x^2` terms, no products of state and control beyond this simple bilinear form — genuinely linear in `x_t` and `u_t` jointly).
- **Quadratic** describes the *cost*: `c(x, u) = x^T Q x + u^T R u`, where `Q` and `R` are fixed symmetric matrices. `x^T Q x` penalizes being far from the origin (assumed to be the target state, without loss of generality — see §2.3 for the case where the target isn't the origin); `u^T R u` penalizes using large control effort.
- **Regulator** is a classical control-theory term for a controller whose job is to drive a system to, and then hold it at, some desired setpoint (here, the origin) and keep it there despite disturbances — as opposed to, say, a controller whose job is to track a moving target (a distinct but related problem, briefly touched in §2.3). "Regulating" a system means stabilizing it at a fixed operating point.

`Q` and `R` are required to be symmetric, and `R` strictly **[positive-definite](https://en.wikipedia.org/wiki/Definite_matrix)** (`Q` need only be positive-*semi*-definite) — meaning `x^T Q x ≥ 0` for all `x` (and `u^T R u > 0` for all nonzero `u`). This is exactly the matrix generalization of "the parabola opens upward, not downward or sideways": a positive-definite quadratic form is a genuine bowl with a unique minimum, whereas an indefinite one (some directions curve up, others down) has a **[saddle point](https://en.wikipedia.org/wiki/Saddle_point)** instead of a minimum — calculus alone can't distinguish a saddle from a minimum, so positive-definiteness is exactly the assumption that makes "set the derivative to zero" a valid way to *minimize* the cost rather than merely find a stationary point.

### 2.2 Deriving the Riccati backward recursion

Apply the Bellman equation of §1 to LQR's specific quadratic cost and linear dynamics, one backward step at a time, tracking a hypothesis that the cost-to-go stays quadratic in the state at every timestep (this hypothesis is confirmed self-consistently as the derivation proceeds — see the boxed insight below).

**Step 1 — base case.** At the final timestep, with no more actions to take, the cost-to-go is just the terminal cost, which is already quadratic:
```
J_0(x) = x^T Q x =: x^T P_0 x
```
(defining `P_0 := Q` purely as notation for "the matrix describing the quadratic cost-to-go at this stage" — the subscript counts backward steps taken so far, not forward time).

**Step 2 — apply the Bellman backup once.** Using the Bellman equation with the LQR dynamics substituted in:
```
J_1(x) = min_u [ x^T Q x + u^T R u + J_0(A x + B u) ]
```

**Step 3 — substitute the quadratic form for `J_0`.** Since `J_0(z) = z^T P_0 z`:
```
J_1(x) = min_u [ x^T Q x + u^T R u + (Ax + Bu)^T P_0 (Ax + Bu) ]
```

**Step 4 — expand and separate the `x`-only term.** Expanding `(Ax+Bu)^T P_0 (Ax+Bu) = x^T A^T P_0 A x + 2 u^T B^T P_0 A x + u^T B^T P_0 B u` and pulling the pure-`x` piece (`x^T Q x + x^T A^T P_0 A x`) out of the minimization (it doesn't depend on `u`):
```
J_1(x) = x^T Q x + x^T A^T P_0 A x + min_u [ u^T R u + 2 u^T B^T P_0 A x + u^T B^T P_0 B u ]
```

**Step 5 — minimize over `u` by calculus.** The bracketed expression is quadratic in `u`; take its gradient with respect to `u` and set it to zero. Using the vector-calculus identities `∂/∂u (u^T M u) = 2Mu` (for symmetric `M`) and `∂/∂u (u^T M b) = M^T b`:
```
∂/∂u [...] = 2Ru + 2 B^T P_0 A x + 2 B^T P_0 B u = 0
⟹ (R + B^T P_0 B) u = -B^T P_0 A x
```

**Step 6 — solve for the optimal control.** `R` is positive-definite and `B^T P_0 B` is positive-semi-definite, so their sum is invertible:
```
u* = -(R + B^T P_0 B)^{-1} B^T P_0 A x =: K_1 x
```
This is the derivation's first payoff: the optimal control at this step is a **linear function of the state** — this is precisely why LQR's control law is called "linear state feedback," and it's the same word "linear" from the name LQR, now describing the *controller* as well as the *dynamics* it was originally describing.

**Step 7 — plug the optimal control back in.** Substituting `u = K_1 x` into the expression from Step 4 and collecting terms:
```
J_1(x) = x^T ( Q + K_1^T R K_1 + (A + B K_1)^T P_0 (A + B K_1) ) x =: x^T P_1 x
```

> **KEY INSIGHT — why the cost-to-go stays quadratic forever.** Look closely at every term inside the parentheses in Step 7: `Q` is quadratic by assumption; `K_1^T R K_1` arose specifically because the *linear-in-`x`* control `u = K_1 x` was substituted back into the *quadratic* cost `u^T R u`, and a linear function squared is quadratic; the last term `(A+BK_1)^T P_0 (A+BK_1)` is manifestly of the form (matrix)`^T` (matrix) sandwiching `x`, i.e. quadratic by construction. Every term is quadratic in `x`, so their sum — the new cost-to-go `J_1` — is quadratic in `x` too, with matrix `P_1`. This means the *hypothesis* "the cost-to-go is quadratic" that Step 1 started with is **exactly reproduced** one step later, just with an updated matrix (`P_0 → P_1`). That self-consistency is the entire reason LQR has a closed form at all: the same six-step calculation can be repeated identically at every backward step, updating only the matrix `P`, all the way from `P_0` to `P_N`, using nothing but matrix algebra — no numerical optimization is ever invoked, because the "solve `∂/∂u = 0`" step is always the same closed-form linear-algebra formula.

The matrix equation relating `P_{n}` to `P_{n-1}` is called the **[Riccati equation](https://en.wikipedia.org/wiki/Riccati_equation)**, and running it backward through the timesteps is the **Riccati recursion**. The name honors **[Jacopo Riccati](https://en.wikipedia.org/wiki/Jacopo_Riccati)**, an 18th-century Venetian mathematician who first studied this general class of nonlinear differential/difference equation (quadratic in the unknown) — long before it had anything to do with control theory; the equation that shows up here is a *discrete-time, matrix-valued* member of that same equation family.

### Algorithm summary: the Riccati recursion

```
P_0 = Q
for n = 1 .. N:
    K_n = -(R + B^T P_{n-1} B)^{-1} B^T P_{n-1} A
    P_n = Q + K_n^T R K_n + (A + B K_n)^T P_{n-1} (A + B K_n)
```
Then, having solved this backward pass once, the optimal control at *any* forward timestep `t` (counting `t` forward from the start, with `n = N - t` backward steps remaining) is read straight off:
```
u_t = K_t x_t
```
— a fixed, precomputed linear gain matrix multiplied by whatever state is actually observed at that step. Note the gains `K_t` in general differ at every timestep (they depend on how many steps remain), giving a **time-varying** linear control law even though the dynamics and cost are themselves time-invariant.

> **Worked example: an omnidirectional vehicle with friction.** Consider a point-mass vehicle moving in a plane under an applied force `u` and linear friction, `m p̈ = u - α ṗ` (position `p`, velocity `ṗ = v`, friction coefficient `α`). Discretizing with a small timestep `h` (forward-Euler: `v_{t+1} ≈ (1 - hα/m) v_t + (h/m) u_t`, `p_{t+1} ≈ p_t + h v_t`) gives exactly the linear form `x_{t+1} = A x_t + B u_t` with state `x_t = [p_t; v_t]`:
> ```
> A = [[1, h], [0, 1 - hα/m]],   B = [[0], [h/m]]
> ```
> (This is the identical vehicle model used in the Stanford ENGR108 lecture notes summarized in §2.2's reading write-up below.) With cost `‖x‖² + ρ‖u‖²` (a special case of `x^T Q x + u^T R u` with `Q = I`, `R = ρI`), the Riccati recursion above produces gains `K_t` that, when applied in a forward simulation from some nonzero initial position/velocity, drive both position and velocity smoothly to zero — and because the optimal control is `u_t = K_t x_t`, the *control itself* shrinks to zero exactly as the state converges, with no separate stopping rule needed. One real limitation this formulation has no way to express: nothing here stops the optimizer from demanding an arbitrarily large force `u` if `Q`, `R` are set to favor fast convergence — real actuators have torque/force limits, and plain LQR has no mechanism for enforcing them (unlike, e.g., MPC with explicit constraints, a direction outside this week's derivations).

### Reading write-up: Somil Bansal's LQR lecture notes

*Citation: Somil Bansal, "EE 221A: Special Lecture on the Linear Quadratic Regulator," UC Berkeley course notes.*

**What this reading derives/argues.** These notes derive exactly the discrete-time, finite-horizon LQR result via dynamic programming/Bellman's principle of optimality, in essentially the same six-step shape as §2.2 above: define the cost-to-go `J*_t(z) = z^T P_t z`, apply the Bellman backup, differentiate the resulting quadratic-in-`u` expression, and solve for the optimal gain `K_t = (R + B^T P_{t+1} B)^{-1} B^T P_{t+1} A`, with `P_t = Q + K_t^T R K_t + (A - B K_t)^T P_{t+1} (A - B K_t)` and boundary condition `P_N = Q_f`. It proves the result formally by backward induction on `t`, explicitly verifying the "quadratic cost-to-go in implies quadratic cost-to-go out" self-consistency that §2.2's boxed insight above explains in words. It also covers two extensions used later in these notes: the **infinite-horizon** case, where the Riccati recursion converges to a steady-state matrix `P_ss` solving the *algebraic* Riccati equation (a fixed point of the recursion rather than a finite backward sweep), yielding a single time-*invariant* gain `K_ss`; and **state-affine systems** `x_{t+1} = Ax_t + Bu_t + c` (dynamics with a constant offset term), handled by augmenting the state with a constant "1" entry to fold the offset back into the standard linear form.

**Main takeaway/argument.** LQR's control law is always linear state feedback, and its cost-to-go is always quadratic — a clean, fully closed-form result that requires nothing beyond matrix algebra to compute, once the recursion is set up correctly.

**How it connects.** This is the direct source of the derivation walked through step-by-step in §2.2 above, and its infinite-horizon extension is exactly what makes the constant-gain feedback law in the Stanford ENGR108 write-up below and its 747 example well-defined.

### Reading write-up: Stanford ENGR108 "Linear-Quadratic Control" slides

*Citation: Jenny Hong, Nicholas Moehle, Stephen Boyd, "Linear-Quadratic Control," ENGR108 lecture slides, Stanford University.*

**What this reading derives/argues.** These slides build up the same LQR machinery through a sequence of increasingly general control problems, all posed as **linearly-constrained least-squares problems**: first minimum-energy state transfer (drive `x_1` to a desired final state `x^des` using minimum `‖u‖²`), then output tracking (`y_t = C x_t` should follow a desired trajectory `y_t^des`, trading off tracking error against control energy via a parameter `ρ`), then waypoint-constrained trajectories, then rendezvous and formation-flying problems for multiple vehicles simultaneously. The specific vehicle-with-friction dynamics used throughout these slides (`m dv/dt = u - ηv`, discretized to the same `x_{t+1} = Ax_t + Bu_t` form) is the exact source of §2.2's worked example above. The slides finish by posing the LQR problem itself (minimize `Σ‖x_t‖² + ρΣ‖u_t‖²` subject to the linear dynamics) and stating its solution as constant linear state feedback `u_t = K x_t`, where `K` is called the **LQR gain matrix**, found by "taking the correct slice" of the inverse of the problem's KKT matrix (an equivalent way of expressing the same Riccati-recursion solution derived in §2.2, arrived at from the least-squares/KKT perspective rather than the dynamic-programming perspective) — the slides note entries of `K` converge as the horizon `T` grows large, consistent with Bansal's infinite-horizon steady-state result above.

**Main takeaway/argument.** A worked numerical example gives this reading's most concrete anchor: linearized longitudinal flight dynamics for a Boeing 747 at 40,000 ft, level flight, 774 ft/sec, with state `x_t = (w_t, v_t, θ_t, q_t)` (body-axis velocity, perpendicular velocity, pitch angle, pitch rate) and control `u_t = (e_t, f_t)` (elevator angle, thrust). For this system (with `A`, `B` matrices given numerically in the slides), the un-controlled ("open-loop," `u_t = 0`) system oscillates indefinitely, while the LQR-controlled ("closed-loop," `u_t = K x_t`) system converges to the origin within roughly 30–50 seconds — a direct, physically concrete demonstration of exactly the "control shrinks to zero as state converges" behavior seen in §2.2's toy vehicle example, here on a real (linearized) aircraft model. The reported gain matrix (for horizon `T = 100`, `ρ = 100`) converges by around `T ≈ 30`, consistent with the infinite-horizon theory above.

**How it connects.** This reading supplies the concrete state-feedback-control-loop picture (Figure: state measured, fed through gain `K`, added back into the dynamics) that makes §2.3's closed-loop discussion and §4's PID-vs-LQR contrast concrete, and its 747 example is referenced again in §2.4 below as the running illustration of LQR's genuine practical value on a real (if linearized) physical system.

### 2.3 Generalizing LQR: affine dynamics, general costs, and noise

Three extensions matter for later sections without changing anything structural in the derivation above:

**Affine dynamics and general (not necessarily origin-centered) costs.** Real targets aren't always the origin, and real dynamics often have a constant offset (e.g. gravity, or a linearization point that isn't the origin — exactly the situation §3 confronts for nonlinear systems). Generalizing to `x_{t+1} = A_t x_t + B_t u_t + b_t` and a cost of the form `[x;u]^T H_t [x;u] + [x;u]^T h_t` (a quadratic-plus-linear cost over the stacked state/control vector) changes nothing about the derivation's logic — the same six-step argument goes through, producing an **affine** control law `u_t = K_t x_t + k_t` (a linear term plus a constant offset) instead of purely linear feedback, with **time-varying gains** `K_t`, `k_t` computed by the same kind of backward recursion. This generalization is exactly what iLQR (§3) needs, since linearizing a nonlinear system around a moving nominal trajectory produces exactly this affine-dynamics, general-quadratic-cost structure at every iteration.

**LQG: adding Gaussian noise.** Suppose the true dynamics have an additive Gaussian disturbance, `x_{t+1} = A_t x_t + B_t u_t + w_t`, with `w_t` drawn independently from a Gaussian distribution at each step (§1's disturbance term `e_t`, specialized to Gaussian). This setting is called **[LQG](https://en.wikipedia.org/wiki/Linear%E2%80%93quadratic%E2%80%93Gaussian_control)** — literally "**L**inear-**Q**uadratic [control] plus **G**aussian [noise]" — the name adds exactly one letter to LQR's name because it adds exactly one new ingredient to the problem: random Gaussian process noise on top of the otherwise-identical linear-dynamics, quadratic-cost setup.

The nontrivial, useful fact LQG delivers: **the optimal control law's functional *form* is completely unchanged** — still `u_t = K_t x_t + k_t`, with the *exact same* gain matrices `K_t` that would be computed while ignoring the noise entirely — as long as the true state `x_t` is directly observed at every step (this is the "closed-loop" qualifier: the controller gets to see and react to the actual, noise-perturbed state before choosing each action, rather than committing to a full open-loop action sequence in advance). This is nontrivial because it means *solving the noisy problem requires no new machinery* — the deterministic Riccati recursion of §2.2 already gives the right answer, and the noise only ever shows up in the resulting *cost*, never in the *control law itself*. (When the state is only noisily or partially observed rather than directly measured, LQG's full solution additionally requires a state estimator — a Kalman filter — feeding its best state estimate into this same LQR gain; that estimation problem is outside this week's scope.)

### 2.4 LQR's value and limits

Weighed against Week 1's BC (§2.2 of `week1-study-notes.md`), LQR sits at the opposite end of nearly every axis:

| | Behavioral cloning (Week 1) | LQR (this week) |
|---|---|---|
| Training data needed | A dataset of expert demonstrations | **None** — zero data, purely computed from a model and a cost |
| Optimality guarantee | None in general (§3.2 of Week 1: error compounds as `T²ε`) | **Provably, exactly globally optimal** for its problem class |
| Task generality | Handles arbitrary tasks the data covers | Restricted to linear dynamics, quadratic cost |
| Constraint handling | Whatever the data implicitly encodes | No native way to encode obstacles or bound controls (§2.2's worked example) |

LQR is not a general-purpose robot controller — most interesting robot dynamics are nonlinear (§3 develops this immediately), most interesting costs are not literally quadratic bowls, and hard constraints (joint limits, obstacle avoidance) don't fit the quadratic-cost mold naturally. But within the box it draws for itself, LQR's guarantee is unconditional: given truly linear dynamics and truly quadratic, positive-definite costs, the Riccati recursion's output is *the* global optimum, not a local one, not an approximation — a strength no learned policy of Week 1's kind can claim without qualification. §3 shows how to stretch LQR's applicability far beyond exactly-linear systems without giving up this machinery entirely.

## 3. From LQR to iLQR: nonlinear dynamics via repeated linearization

Most real robot dynamics are not linear. Contrast two vehicle models used already in these notes: the omnidirectional vehicle-with-friction of §2.2's worked example has dynamics `x_{t+1} = Ax_t + Bu_t` with constant matrices `A = I`, `B = δt·I` (approximately) — genuinely linear, exactly LQR's assumption. A simple car (a standard robotics kinematic model, sometimes called the "unicycle model" for its two independent controls), by contrast, has dynamics `ẋ = v cos θ`, `ẏ = v sin θ`, `θ̇ = ω` (position `x, y`, heading `θ`, forward speed `v`, turn rate `ω`) — and here the *effect* of the controls `(v, ω)` on `(ẋ, ẏ)` depends on the current heading `θ_t` through `cos θ_t` and `sin θ_t`. That dependence of the effective "B matrix" on the current state is exactly what "nonlinear" means here, and it is the norm, not the exception, for real robots: legged robots, manipulator arms swinging through different configurations, and any vehicle that turns all have dynamics that depend on the current state in a genuinely nonlinear way.

**The core trick, via a Newton's-method analogy.** Recall (or take on faith, since this is a standard root-finding method) that **[Newton's method](https://en.wikipedia.org/wiki/Newton%27s_method)** finds the root of a nonlinear function by repeatedly: approximating the function *locally* as linear (its tangent line) around the current guess, solving the resulting easy linear problem exactly, and moving to that solution as the new guess — then repeating, since the tangent-line approximation is only good *near* the point it was built at.

**Iterative LQR ([iLQR](https://en.wikipedia.org/wiki/Differential_dynamic_programming))** applies exactly this idea to nonlinear optimal control: approximate the nonlinear problem *locally* as a linear-quadratic one around a current guess at the trajectory (the **nominal trajectory** — "nominal" meaning "the trajectory currently being treated as the reference/candidate solution," not yet verified to be correct, exactly as "nominal value" means "the stated/assumed value" in everyday usage), solve that local linear-quadratic problem *exactly* via the LQR machinery of §2 (now using §2.3's affine-dynamics, general-quadratic-cost generalization), use the solution to update the nominal trajectory, and repeat until convergence.

### Deriving one iLQR iteration

**Linearize the dynamics.** Around the current nominal trajectory `(x̄_t, ū_t)`, take a first-order **[Taylor expansion](https://en.wikipedia.org/wiki/Taylor%27s_theorem)** of the true (nonlinear) dynamics `f`:
```
f(x, u) ≈ f(x̄_t, ū_t) + A_t (x - x̄_t) + B_t (u - ū_t)
```
where `A_t = ∂f/∂x` and `B_t = ∂f/∂u`, the **[Jacobians](https://en.wikipedia.org/wiki/Jacobian_matrix_and_determinant)** of `f` evaluated at the nominal point — this is exactly why the car example above has a state-dependent effective `B_t`: differentiating `v cos θ` with respect to `v` gives `cos θ_t`, which depends on where along the nominal trajectory this Jacobian is evaluated. Writing the deviations as `δx_t = x_t - x̄_t`, `δu_t = u_t - ū_t`, this linearization takes exactly the affine form `δx_{t+1} = A_t δx_t + B_t δu_t` that §2.3 already extended LQR to handle.

**Expand the cost to second order.** Similarly Taylor-expand the (possibly nonlinear) true cost around the nominal trajectory, keeping terms up to *second* order in the deviations (a gradient term `h_t` and a Hessian term `H_t`, matching §2.3's general quadratic-plus-linear cost form over `[δx; δu]`) — a first-order expansion wouldn't be enough here, since a cost with zero curvature information gives the inner LQR problem nothing to optimize.

**Solve the local LQR problem.** Run the backward Riccati recursion and forward pass of §2.2/§2.3 on this linearized-dynamics, quadratic-cost-in-deviations problem, producing an optimal deviation `δu_t` at every timestep (via the affine control law `δu_t = K_t δx_t + k_t`).

**Update the nominal trajectory.** Apply the found deviations: `ū_t ← ū_t + δu_t`, roll the true nonlinear dynamics forward from the updated controls to get a new nominal state trajectory, and repeat the whole linearize-solve-update cycle until the nominal trajectory stops changing (convergence).

### Trust regions: why the linear approximation can go stale

The iLQR update above has a gap: nothing stops the newly computed `δu_t` from being *large*, and a first-order Taylor expansion is only accurate *near* the point it was built at (exactly Newton's method's own well-known failure mode) — so a large update can walk the nominal trajectory somewhere the original linearization no longer describes the true dynamics or cost accurately at all, making the "solution" to the local LQR problem actively unhelpful, or the next iteration wildly unstable.

The fix is called a **[trust region](https://en.wikipedia.org/wiki/Trust_region)**, and the name is literal: the algorithm should only "trust" its local linear/quadratic approximation within some neighborhood of the point it was built at, and should be actively discouraged from proposing an update that leaves that neighborhood. Concretely, this is implemented by adding a regularization term to the local cost that penalizes large deviations directly:
```
(1 - α) c̃(δx, δu) + α (‖δx‖² + ‖δu‖²)
```
where `c̃` is the second-order Taylor-approximated cost from above and `α ∈ [0, 1]` is a tunable weight: as `α` increases, the optimizer is pushed harder toward keeping `δx`, `δu` small (staying inside the trusted region), at the cost of making less aggressive progress per iteration.

Even with this safeguard, iLQR loses one of LQR's headline guarantees: because the true problem is nonlinear, iLQR's repeated local linearizations can converge to a **local** optimum that depends on where the iteration started, and the cost's Hessian along the way is not guaranteed to stay positive-definite the way `Q`, `R` were assumed to be in §2.1 (a non-positive-definite local Hessian corresponds to the local quadratic approximation being a saddle rather than a bowl, exactly the failure mode §2.1's positive-definiteness assumption was designed to rule out). This is the direct cost of buying nonlinear applicability: LQR's *single, guaranteed global optimum* becomes iLQR's *a* locally optimal solution, generally different depending on the initial nominal trajectory.

### Paper Breakdown: Iterative LQR for Nonlinear Biological Movement Systems (Li & Todorov)

*Citation: Weiwei Li, Emanuel Todorov, "Iterative Linear Quadratic Regulator Design for Nonlinear Biological Movement Systems," Proceedings of the 1st International Conference on Informatics in Control, Automation and Robotics (ICINCO), 2004.*

**Problem/motivation.** Biological motor control (how animals plan reaching movements) is naturally modeled as stochastic optimal feedback control, but existing such models "rely on the Linear-Quadratic-Gaussian formalism, while in reality biomechanical systems are strongly non-linear." Prior nonlinear approaches based on Bellman's optimality principle (solving the Hamilton-Jacobi-Bellman PDE directly) suffer the curse of dimensionality and are infeasible for realistically high-dimensional biomechanical models.

**Key idea/innovation.** Exactly the iLQR recipe derived above: iteratively linearize the nonlinear dynamics around a nominal trajectory and solve a "modified LQR technique" on the linearization, using the result to improve the nominal trajectory, repeated to convergence. (Historical note: this is the paper that first introduced and named the iLQR method used throughout this section and referenced again in §6 and §9.)

**Method & training procedure.** The paper's derivation, while arriving at the same fixed point as §2.2/§3 above, takes a Pontryagin/costate route rather than the Bellman-cost-to-go route used in these notes: it introduces a Lagrange multiplier ("costate") `δλ_k` via a discrete Hamiltonian, derives a linear two-point boundary-value ("Hamiltonian") system coupling the state and costate deviations, and posits (then verifies) an ansatz `δλ_k = S_k δx_k + v_k`; substituting this ansatz into the Hamiltonian system and applying the matrix inversion lemma yields the optimal control update `δu_k = -K δx_k - K_v v_{k+1} - K_u u_k`, with `K`, `S_k` following a backward Riccati-style recursion identical in spirit to §2.2's, plus an extra auxiliary term `v_k` (absent from the pure-regulator case) that arises because the paper's nominal control `u_k` need not be zero at the linearization point, i.e. it directly derives §2.3's affine-control-law generalization rather than treating it as a separate extension. The nonlinear system studied is a 2-link, 6-muscle biomechanical arm model (10 state dimensions: 2 joint angles, 2 joint velocities, 6 muscle activations; 6 controls, one per muscle group), with cost `(θ(T) - θ*)^T(θ(T) - θ*) + r∫u^Tu dt` (a reaching cost plus an energy-efficiency term), compared against a simpler 2-DOF torque-controlled arm and a 1-DOF inverted pendulum swing-up task.

**Results.** On all three test systems (torque-controlled arm, muscle-controlled arm, inverted pendulum), iLQR converged to a better (lower-cost) solution than all three existing comparison methods (a boundary-value ODE solver, conjugate gradient descent using Pontryagin's-principle gradients, and differential dynamic programming) — and converged in dramatically less CPU time. Concrete numbers from the paper's Table 1: on the muscle-controlled arm (the hardest, highest-dimensional case), iLQR reached a lower final cost (`2.37e-05`) than conjugate gradient descent (`5.16e-05`, 70.09 sec) and differential dynamic programming (`8.35e-05`, 184.84 sec) while taking only `6.62` sec — over a **10× speedup** over the nearest competitor, matching the paper's own claim that "the speed advantage is most notable in the complex arm model, where ILQR outperformed the nearest competitor by more than a factor of 10." On the inverted pendulum, iLQR reached cost `0.0096` in `0.48` sec versus differential dynamic programming's `2.6611` in `2.28` sec. The paper also demonstrates the algorithm scaling to 100 randomly-initialized starting trajectories converging reliably to low-cost solutions (Figure 5), and explicitly flags local minima as an open issue: "it may be necessary to combine ILQR with global search methods (e.g. using multiple restarts)" — exactly the local-optimum caveat this section's derivation above already anticipated.

**How it connects.** This paper is the direct source of the iLQR derivation walked through above, and its "modified LQR technique run on a repeatedly-relinearized nominal trajectory" is exactly the machinery §6's differentiable-physics Paper Breakdown (Belbute-Peres et al.) later reuses off-the-shelf as its own planner, and exactly the classical planning layer §9.4 argues persists underneath even the most modern neural-network-heavy model-based RL pipelines.

## 4. Feedback via replanning: closed-loop control and MPC

Both LQR (§2) and iLQR (§3), as derived so far, compute a *whole action sequence up front* and are described as **[open-loop](https://en.wikipedia.org/wiki/Open-loop_controller)** in one specific sense worth being careful about: the *sequence of gains* `K_t` is computed once, assuming the dynamics model is perfectly accurate — but LQR/LQG's actual *execution*, `u_t = K_t x_t`, does re-measure the true state `x_t` at every step (that's the "closed-loop" feedback §2.3 already described). The remaining gap iLQR has that pure LQR does not: iLQR's nominal trajectory and its linearizations were computed assuming the nonlinear model is exact and no unmodeled disturbance pushes the real system off that specific nominal path — if reality departs from that one planned path (nonlinear model error, an unexpected push, a moving target), continuing to blindly apply the *originally planned* action sequence past that point is exactly like closing your eyes while walking a route you memorized: fine until something in the real world doesn't match what you memorized, at which point you have no mechanism for noticing or correcting.

The direct fix: **replan**. Instead of computing one action sequence once and executing all of it, repeatedly re-observe the current true state and re-solve the optimal-control problem from there, executing only the very next action before replanning again. This closes the loop at the level of the *planning* process itself, not just at the level of executing a precomputed gain — the plan itself gets to change based on what's actually observed, not just the numeric action value.

**The MPC loop:**
1. Observe the current true state `x_0`.
2. Solve the (LQR or iLQR) optimal-control problem over some finite lookahead window, starting from `x_0`.
3. Execute *only the first action* `u_0` of the resulting plan.
4. Advance one timestep, observe the new true state, and repeat from step 2.

This procedure is called **[Model Predictive Control (MPC)](https://en.wikipedia.org/wiki/Model_predictive_control)**, and its defining loop is also called **receding horizon control** — "receding" is concrete and literal here: the lookahead window (the horizon) always spans the same *number* of steps into the future, but because the whole window slides forward by one step every time the controller replans, the window's *endpoint* keeps retreating ("receding") further into the future in absolute time, always staying a fixed distance ahead of the ever-advancing present. MPC is the general strategy name; "receding horizon control" describes the same thing by naming what the horizon visibly does as the controller runs.

**Why this helps, concretely:** any mismatch between the model used for planning and the true dynamics — nonlinearity poorly captured by one linearization, an unmodeled disturbance, a target that moved — gets corrected at the very next replanning step, because the plan is always recomputed starting from where the robot *actually* is, not from where an old plan predicted it would be.

**Making MPC fast enough to run in real time.** Solving a full trajectory-optimization problem from scratch at every single control step (potentially hundreds of times per second) is expensive; several standard speedups make this practical:
- **Shorter horizons** — planning only a few steps ahead is cheaper per replan, at the cost of being more shortsighted about the far future (mitigated by a good terminal cost approximating "cost-to-go beyond the horizon," §1's cost-to-go concept resurfacing here directly).
- **Executing more than one planned action** before replanning — trades off responsiveness for computational savings.
- **Warm starts** — since consecutive replanning problems are nearly identical (the world changed only slightly in one timestep), initialize each new optimization from the *previous* solution (shifted forward by one step) rather than from scratch. This is called a "warm start" by analogy to a warm-started engine that's already near its running state, versus a "cold start" beginning from nothing — reusing the previous near-optimal answer as a very good initial guess dramatically cuts the number of optimization iterations needed to converge on the new, very similar problem.
- **Faster or custom optimizers** — §6's MPCGPU Paper Breakdown is a concrete example of squeezing much more speed out of the underlying linear-algebra solve itself via GPU parallelization.

### PID vs. LQR: a concrete contrast in how gains get chosen

A useful point of comparison, since both are genuinely used as robot controllers: a **[PID controller](https://en.wikipedia.org/wiki/PID_controller)** (Proportional-Integral-Derivative) is a classical feedback controller that reacts to the error between the current and desired value of *one* variable at a time, using hand-tuned gains for each of the three terms (how strongly to react to the current error, the accumulated past error, and the rate of change of the error). PID's gains are typically **tuned manually or by trial-and-error** ("gain scheduling" — manually switching gain sets for different operating regimes) per variable, are only locally valid (tuned around one operating point), and come with **no global optimality or stability guarantee** for a general nonlinear system.

LQR's gain matrix `K`, by contrast, is **systematically derived** from an explicit dynamics model and cost function via the Riccati recursion (§2.2), simultaneously accounts for *coupling between multiple state variables* (rather than controlling each one independently the way PID typically does), and comes with LQR's full global-optimality guarantee (§2.4) for the linear-quadratic problem it was derived for. This is the first half of framing question (4) — **is optimal control "obsolete" machinery, or does it remain foundational?** — previewed here and answered in full in §9.4: PID represents the "hand-tuned, ad hoc" end of classical control, while LQR represents the "systematically optimal, model-based" end, and modern learned/neural methods sit in a third, still-being-worked-out relationship to both, which §9.4 develops using this week's later material as evidence.

### Reading write-up: Rawlings' "Tutorial Overview of Model Predictive Control"

*Citation: J. B. Rawlings, "Tutorial Overview of Model Predictive Control," IEEE Control Systems Magazine, 20(3), 2000.*

**What this reading derives/argues.** This tutorial surveys MPC's core idea — repeatedly solving a finite-horizon optimal control problem online and applying only the first computed input, exactly the loop derived above — tracing its origins to industrial process control in chemical plants and oil refineries during the 1980s, where large time delays, high-order dynamics, and hard operating constraints made classical single-loop controllers (like PID) inadequate. The tutorial's throughline is MPC's defining structural advantage over such classical controllers: because MPC explicitly optimizes over a predicted future trajectory using an explicit model, it can *anticipate* future disturbances or setpoint changes and act on them in advance, rather than only reacting to error already observed — the model-based, "look-ahead" version of feedback control, as opposed to purely reactive schemes.

**Main takeaway/argument.** MPC's central practical strength is handling explicit constraints (actuator limits, safety bounds) directly inside the optimization at every replanning step — precisely the capability §2.4 flagged as missing from plain LQR — at the cost of needing to solve a (potentially nonlinear, constrained) optimization problem online, repeatedly, fast enough to keep up with the control rate; the tutorial frames much of the field's subsequent research effort as chasing faster, more reliable ways to solve exactly that repeated optimization problem.

**How it connects.** This reading is the direct historical and conceptual anchor for the MPC loop and receding-horizon terminology derived in this section, and its emphasis on constraint-handling and computational speed directly motivates §6's sampling-based planners (MPPI, CEM) and §6's GPU-parallelized solvers (MPCGPU, STORM) as two different modern answers to "how do we solve the online optimization fast enough."

## 5. Learning the dynamics model — the bridge to "world models"

Everything so far (§2–§4) assumed the dynamics `f` is *known* exactly. Real robots rarely have this luxury: contact, friction, deformable objects, and fluids are all notoriously hard to model in closed form by hand — and even the "known" car-vs-omnidirectional-vehicle nonlinearity contrast from §3 is a reminder that even *fully specified, analytically derived* dynamics for something as simple as a turning vehicle are already nonlinear; real robots with joints, contacts, and unmodeled compliance are harder still. This section asks the obvious next question: what if `f` itself has to be **learned from data**, so that everything §2–§4 built (LQR, iLQR, MPC) can run on the *learned* model instead of a hand-derived one?

**The naive approach.** Collect a dataset of observed transitions `D = {(x_t, u_t, x_{t+1})}` by executing some (possibly random, possibly partially-controlled) actions on the real robot, then fit a function `f_θ` by ordinary regression, minimizing:
```
Σ ‖ f_θ(x_t, u_t) - x_{t+1} ‖²
```
This is worth pausing on explicitly: it is **the exact same supervised-learning setup as Week 1's behavioral cloning** (§2.2 of `week1-study-notes.md`) — a neural network fit by an ordinary regression loss to (input, output) pairs collected from the real system — just with the *regression target* swapped from "the expert's action" to "the next state." Every general lesson about supervised learning (overfitting, the need for representative training data, standard training loops) applies here unchanged; the only thing that's new is *what* is being predicted.

Two refinements make this naive recipe substantially more practical:

**(a) Multi-step prediction loss instead of single-step.** Training `f_θ` to be accurate one step at a time (minimizing single-step prediction error, as above) does not guarantee it stays accurate when *rolled out* for many steps in a row during planning — small single-step errors compound as the model's own (possibly slightly wrong) predicted next state gets fed back in as the input to predict the state after that, again and again. This is **precisely the same compounding-error phenomenon Week 1 formalized for behavioral cloning** in its covariate-shift discussion (§3.2 of `week1-study-notes.md`, where a per-step error rate `ε` compounds to `T²ε` total cost over a horizon `T` because early errors push the policy into states its training distribution never covered) — here the "policy" being rolled out is the dynamics model itself, and the "states it was never trained on" are the model's own accumulating prediction errors feeding back into its own input. The direct fix, mirroring DAgger's fix for BC, is to train on **multi-step rollout error** rather than single-step error: unroll the model for several steps starting from a real state, compare the *entire predicted trajectory* against the real one, and backpropagate through the whole unrolled sequence — directly penalizing the compounding-error behavior the model will actually be evaluated under at planning time, not just its single-step accuracy. (Best-effort citation: Venkatraman, Hebert & Bagnell, "Improving Multi-step Prediction of Learned Time Series Models," is the literature's standard reference for this fix — the specific technical details of that paper are not independently verified here, but the core idea it's cited for, training on multi-step rather than single-step rollout error to combat compounding model error, is exactly the fix described above.)

**(b) Predicting `Δx` instead of the next state directly.** Rather than training `f_θ(x_t, u_t)` to output the *absolute* next state `x_{t+1}`, train it to output the *change* `Δx_t = x_{t+1} - x_t` and reconstruct `x_{t+1} = x_t + Δx_t`. This is usually an easier regression target because, for most physical systems evolving under a reasonably small timestep, the change per step is much smaller in magnitude and much more consistently distributed than the absolute next state (which, over a long trajectory, can range over the system's entire state space) — a smaller-magnitude, more consistently-scaled target is generally easier for a network to fit accurately. This is exactly what PILCO (already summarized in §7 below) does: its Gaussian Process is trained on `(x_{t-1}, u_{t-1}) → Δ_t = x_t - x_{t-1} + ε`, predicting the change rather than the absolute state.

### "World models" are learned dynamics models — nothing more

The term **[world model](https://en.wikipedia.org/wiki/World_model)**, used throughout the model-based RL literature (and in this week's PlaNet paper, §7 below), names *exactly* the learned function `f_θ` just described — often, as PlaNet demonstrates concretely, over a **learned latent (compressed) state** rather than the raw observation, but conceptually the same object: a model that predicts how the external world's state evolves in response to actions. The word "world" in "world model" is doing one specific piece of contrastive work: it emphasizes that this network's job is to capture how the *environment* evolves, as opposed to a "policy model," whose job is to map observations directly to actions. Every "world model" in this literature is a learned dynamics model in the §5 sense above; the two phrases are synonyms, and this week's notes will use them interchangeably from here on, always with "world model = learned `f_θ`" in mind.

### The model-based RL loop

Putting §5's model-learning together with §2–§4's planning machinery gives the general **model-based reinforcement learning** recipe that every Paper Breakdown in §7 and §8 instantiates in some form:

1. **Collect** an initial dataset `D` of transitions (e.g. via random or exploratory actions on the real system).
2. **Fit** the dynamics model `f_θ` on `D` (§5's regression recipe, possibly with the multi-step or `Δx` refinements above).
3. **Plan** through `f_θ` using any of §2–§6's tools (LQR/iLQR if `f_θ` is differentiable and locally well-behaved; MPPI/CEM, §6, if not) to produce a candidate action sequence.
4. **Execute** only the first action (exactly MPC's receding-horizon loop, §4) and observe the new real state.
5. **Append** the newly observed real transition to `D`, and return to step 2 to refit the model on the growing dataset.

This loop is the connective spine for every Paper Breakdown that follows: §7's PILCO, the Gamboa Higuera et al. paper, PETS, and DPI-Nets are all instances of this exact loop with different choices for steps 2 and 3; §8's SLBO, MBPO, and VaGraM are all about making step 2 (and its interaction with step 3) more theoretically principled.

## 6. Planning without gradients: MPPI and CEM

iLQR (§3) has requirements that a learned dynamics model (§5) frequently cannot satisfy. Recall exactly what iLQR's derivation needed: the Jacobians `∂f/∂x`, `∂f/∂u` at every point along the nominal trajectory (Step "linearize the dynamics" in §3), and a cost whose local Hessian is well-behaved enough for the inner LQR solve to make sense (§2.1's positive-definiteness requirement, carried into §3's second-order cost expansion). Three concrete ways a learned or black-box model breaks these requirements:

- A learned neural-network dynamics model can be **noisy or non-smooth** in ways that make its numerically- or automatically-computed gradients unreliable or uninformative, even where they technically exist.
- A **black-box physics/contact simulator** (many robotics simulators, especially ones with contact and collision) may expose no usable gradients at all — the simulation is a sequence of branching, non-differentiable operations (e.g. "did these two objects collide this step, yes/no").
- Costs like **collision indicators** or **sparse goal-reached indicators** are inherently discontinuous — a gradient with respect to trajectory parameters is either zero almost everywhere or simply doesn't exist at the discontinuity.

§6.1 below (differentiable physics) shows one way to fix this directly, by engineering the simulator itself to expose usable analytic gradients even through contact. This section takes the *other* available route: give up on gradients of the model entirely, and replace calculus with **search by simulation**.

### Reframing: evaluate-and-search over sampled trajectories

Week 1's energy-based policies (§7.3 of `week1-study-notes.md`) drew a sharp architectural line between two ways to produce an action: an *explicit* network that predicts an action directly in one forward pass, versus an *energy-based* network that only ever *scores* candidate actions, with the actual action obtained by searching over candidates for the lowest-scoring one — "evaluate-and-search," in that section's own words, rather than "predict-directly." **MPPI** and **[CEM](https://en.wikipedia.org/wiki/Cross-entropy_method)** (Model Predictive Path Integral control and the Cross-Entropy Method, both derived in full below), this section's two planners, apply exactly the same evaluate-and-search dichotomy one level up — not to a single action, but to an entire *trajectory* of actions: rather than computing the optimal action sequence via calculus (as iLQR does), sample many candidate action sequences, *evaluate* each one by simulating it forward through the (possibly non-differentiable) model and scoring its total cost, and use those scores to concentrate the search toward better sequences — "don't differentiate — sample, simulate, and average" (or, for CEM, "sample, simulate, and select").

### MPPI: soft-weighted averaging of sampled rollouts

At each replanning step, MPPI maintains a nominal control sequence `ū_t` (initialized, e.g., from the previous replan's solution, shifted — exactly MPC's warm-start idea from §4) and proceeds:

**Sample.** Draw `K` random perturbations around the nominal sequence: `u^k_t = ū_t + ε^k_t`, with `ε^k_t ~ N(0, Σ)` drawn independently for each of the `K` candidate sequences and each timestep.

**Simulate and score.** Roll each of the `K` perturbed action sequences forward through the (learned or known) dynamics model, accumulating a total cost per rollout:
```
S_k = Σ_t c(x^k_t, u^k_t) + c_N(x^k_N)
```
(running cost summed over the horizon, plus a terminal cost `c_N`, exactly analogous to §2's finite-horizon LQR cost).

**Reweight.** Convert the `K` rollout costs into importance weights via a **softmin** (the same operation as the familiar classifier softmax, but over *negative* cost so lower cost gets *higher* weight, and with an explicit temperature parameter `λ`):
```
w_k = exp( -(1/λ)(S_k - min_j S_j) ) / Σ_j exp( -(1/λ)(S_j - min_j S_j) )
```
(subtracting `min_j S_j` before exponentiating is a standard numerical-stability trick — it doesn't change the resulting weights, since it's a constant shift that cancels between the numerator and denominator, but it keeps the exponentials from overflowing.)

**Update the nominal sequence.** Take a weighted average of the sampled perturbations, weighted by how well each one scored, and shift the nominal sequence toward it:
```
ū_t ← ū_t + Σ_k w_k ε^k_t
```

**Execute and repeat.** Execute only `ū_0` (MPC's receding-horizon step, §4), shift the nominal sequence forward by one step (dropping the now-executed first entry, appending a new guess at the end), and repeat the whole sample-simulate-reweight-update cycle at the next timestep.

> **Demystifying the softmin: it's a familiar operation in an unfamiliar place.** The reweighting step above has *exactly* the same mathematical shape as an ordinary classifier's softmax over negative cost (equivalently, over reward) with a temperature parameter — precisely the softmax the reader already knows from ordinary neural-network classification heads, just applied over sampled *trajectories* instead of class logits. The temperature `λ` controls how "hard" or "soft" the resulting selection is, with two clean limits: as **`λ → 0`**, the weight on the single lowest-cost sample dominates completely (the softmin sharpens into a hard `argmin` — only the very best sampled rollout influences the update, exactly like a low-temperature softmax collapsing onto the single highest-logit class); as **`λ → ∞`**, all the exponentials flatten toward equal values regardless of their cost differences, so the weights become uniform and the update becomes a plain, unweighted average over *all* sampled perturbations, regardless of how good or bad they scored (all information from the cost is discarded). Practical MPPI runs at some intermediate `λ`, softly favoring lower-cost rollouts without discarding the information in the less-good ones entirely.

**Why "path integral."** MPPI stands for **Model Predictive Path Integral** control, and the "path integral" piece of the name traces back to a reformulation of stochastic optimal control (from statistical mechanics/physics) in which the optimal control law can be expressed as an *expectation over sampled trajectories* ("paths") — formally, an integral over the space of all possible paths a system could take, weighted by how good each path is, which is literally a **[path integral](https://en.wikipedia.org/wiki/Path_integral_formulation)** in the mathematical sense the term is used in physics. The full derivation connecting stochastic optimal control to this path-integral expectation is out of scope for these notes, but the softmin-weighted-average update above is precisely a Monte Carlo (sampling-based) estimate of that theoretical expectation-over-paths — which is why the word "path integral" appears in the algorithm's name at all, even though nothing here requires understanding the underlying physics derivation.

> **Worked example: point-mass goal-reaching with friction.** Take the same point-mass-with-friction dynamics as §2.2's worked example, `m p̈ = u - α ṗ`, now with a goal-reaching cost `‖p - p_goal‖²_Q + ‖ṗ‖² + ‖u‖²_R` (penalizing distance to a target position, non-zero velocity, and control effort). Early in a run, the `K` sampled rollouts fan out in many directions around the current nominal guess — some heading roughly toward the goal, others wandering off, others overshooting. Scoring each by total accumulated cost and applying the softmin concentrates weight heavily on whichever handful of samples actually made good progress toward `p_goal` while not overspending on control effort; averaging those (weighted) perturbations back into the nominal sequence bends the nominal trajectory noticeably toward the better-scoring rollouts without committing entirely to any single one of them. As the nominal sequence converges near a genuinely good solution over successive MPC replanning steps, the sampled rollouts increasingly cluster tightly around it (since they're perturbations of an already-good nominal), and the executed path smoothly approaches and settles at the goal, mirroring the same "controls shrink as the state converges" qualitative behavior seen in §2.2's LQR example — but arrived at by repeated sampling and averaging rather than by any closed-form gain matrix.

### CEM: hard selection of "elite" samples

The **[Cross-Entropy Method (CEM)](https://en.wikipedia.org/wiki/Cross-entropy_method)** takes the same evaluate-and-search shape as MPPI but replaces MPPI's *soft*, every-sample-contributes weighting with a *hard* cutoff that only keeps the best few samples:

**Maintain a Gaussian belief.** Represent the current guess at a good action sequence not as a single nominal trajectory but as a full Gaussian distribution over action sequences, `q(u_{0:N-1}) = N(μ, Σ)`.

**Sample, simulate, and score.** Draw `K` action sequences from `q`, roll each forward through the model, and compute each one's total cost — identical to MPPI's sample-and-score steps.

**Select the elites.** Keep only the `M ≪ K` sequences with the *lowest* total cost — these are called the **elites**, a term borrowed directly from evolutionary computation/**[genetic algorithms](https://en.wikipedia.org/wiki/Genetic_algorithm)**, where "elitism" names the strategy of always carrying the best-performing candidates of a generation forward unchanged (or, as here, using them to define the next generation's search distribution) rather than risking losing them to random variation.

**Refit the Gaussian.** Recompute `μ` and `Σ` as the empirical mean and covariance of *only* the elite sequences:
```
μ_t ← (1/M) Σ_{elites} u^k_t
Σ_t ← (1/M) Σ_{elites} (u^k_t - μ_t)(u^k_t - μ_t)^T
```

**Execute and repeat.** Execute `μ_0` (again, MPC's receding-horizon step), shift the distribution forward, and repeat.

**Where the name "cross-entropy" actually comes from.** The refitting step above — computing the empirical mean and covariance of the elite samples — is not an arbitrary choice; it is *exactly* the **[maximum-likelihood estimate (MLE)](https://en.wikipedia.org/wiki/Maximum_likelihood_estimation)** of a Gaussian's parameters given a set of samples (the sample mean and sample covariance are the closed-form MLE solution for a Gaussian's `μ`, `Σ`). Separately, a standard, general result in information theory is that **maximum-likelihood fitting is mathematically equivalent to minimizing the [cross-entropy](https://en.wikipedia.org/wiki/Cross-entropy)** between the empirical distribution of the observed data (here, the elite samples) and the fitted model distribution `q` — this equivalence holds for MLE fitting in general, not anything specific to CEM. Since CEM's refitting step *is* an MLE fit of `q` to the elite empirical distribution, it is *therefore* implicitly minimizing the cross-entropy between the elite samples' empirical distribution and the fitted Gaussian at every iteration — which is precisely where the method's name comes from, even though no cross-entropy loss is ever written down explicitly in the algorithm as stated above. (Historical note: CEM originates from Reuven Rubinstein's 1997 work on **rare-event simulation** — estimating the probability of statistically rare events by iteratively re-fitting a sampling distribution toward the rare region of interest; in that original setting, "rare event" meant a literal low-probability tail event, while in CEM's use here as a planner, the analogous "rare event" being homed in on is simply "cost below the current best threshold," which starts out genuinely rare under the initial, wide sampling distribution and becomes less rare as the distribution refits toward it.)

### MPPI vs. CEM

| | MPPI | CEM |
|---|---|---|
| What is updated | A single nominal mean sequence `ū_t` | A full Gaussian `(μ, Σ)`, including covariance |
| How samples are used | *All* `K` samples contribute, soft-weighted by `w_k` | Only the top `M` "elite" samples contribute; the rest are discarded |
| Iterations per replan | Typically one sample-score-update pass per control step | Often several sample-score-refit iterations per control step, refining the same distribution before executing |
| Hyperparameters | Temperature `λ`, noise covariance `Σ` | Elite fraction `M/K`, number of refit iterations |
| Behavior | Smooth, gradual shifts; robust to noisy per-sample cost estimates since every sample still contributes something | Can concentrate quickly around a promising region, but a hard cutoff risks prematurely discarding a noisy-but-actually-good sample or collapsing `Σ` too early |

The exploitative-versus-robust intuition: CEM's hard elite cutoff lets it concentrate the search distribution quickly once it finds a promising region, but that same hard cutoff means a single unlucky (noisy) high-cost score on an actually-good sample gets it discarded outright, and the resulting covariance estimate is based on only a handful of points, so it can be noisy or collapse prematurely. MPPI's soft weighting never fully discards any sample, which makes it more robust to noisy per-rollout cost estimates (a noisy but genuinely mediocre sample still gets *some* small weight, rather than none, and an unlucky good one isn't zeroed out entirely) at the cost of concentrating more slowly. This is loosely the same **[bias-variance](https://en.wikipedia.org/wiki/Bias%E2%80%93variance_tradeoff)** flavor of tradeoff seen elsewhere in statistics: a harder cutoff (CEM) reduces bias toward mediocre samples faster but increases the variance of the resulting estimate; a softer weighting (MPPI) is a more biased-toward-the-full-sample-population but lower-variance estimate.

### GPU parallelization: why sampling-based planners scale so well

Both MPPI and CEM share a property that makes them extremely amenable to modern hardware: the `K` rollouts, given the current nominal sequence or sampling distribution, are **[embarrassingly parallel](https://en.wikipedia.org/wiki/Embarrassingly_parallel)** — each rollout only needs to simulate its own sampled action sequence forward through the (shared, read-only) dynamics model and compute its own cost, with *zero communication* between rollouts until the very last step (aggregating all `K` scores into the reweighting or elite-selection step). This maps directly onto a GPU's strength: thousands of simple, independent threads doing the same computation (simulate one rollout) on different data (one sampled action sequence each), with a single synchronization point only at the end to combine results. This is precisely why sampling-based MPC has become increasingly practical for real-time robot control as GPU hardware has become ubiquitous, and it's the direct motivation for the next two Paper Breakdowns.

### Paper Breakdown: MPCGPU

*Citation: Emre Adabag, Miloni Atal, William Gerard, Brian Plancher, "MPCGPU: Real-Time Nonlinear Model Predictive Control through Preconditioned Conjugate Gradient on the GPU," arXiv:2309.08079, 2024.*

**Problem/motivation.** Nonlinear MPC is state-of-the-art for locomotion and manipulation, but its performance is bottlenecked by needing to solve a moderately-large, sparse trajectory-optimization problem at every single control step, in real time; most existing GPU-accelerated approaches for this either expose limited natural parallelism (shooting methods) or only give modest speedups on the underlying sparse linear-system solves that direct trajectory-optimization methods reduce to.

**Key idea/innovation.** A custom, GPU-accelerated linear-system solver — a **[Preconditioned Conjugate Gradient (PCG)](https://en.wikipedia.org/wiki/Conjugate_gradient_method)** method specifically tuned for the block-tridiagonal structure of the Schur complement arising from direct trajectory optimization's Karush-Kuhn-Tucker (KKT) system — combined with a GPU-parallel line search, so that essentially every step of the underlying nonlinear-programming solve is done in parallel on the GPU rather than the CPU. Crucially, note the contrast with §6's sampling-based planners above: **MPCGPU is gradient-based**, not sampling-based — it parallelizes the *linear algebra inside a Newton-style optimization solve* (the same general family of algorithm iLQR belongs to, §3), rather than parallelizing independent forward rollouts the way MPPI/CEM do. It's a different, complementary source of GPU speedup, not a competing sampling-based method.

**Method & training procedure.** (No learning is involved here — "training procedure" in this reading's adapted sense means the solver pipeline.) At each control step: (1) compute, in parallel on the GPU, the block-tridiagonal Schur complement `S`, right-hand side `γ`, and a preconditioner `Φ⁻¹` from the linearized dynamics and quadratic cost (exactly the KKT system arising from a direct trajectory-optimization formulation, structurally similar to the affine-dynamics, quadratic-cost problems solved by LQR/iLQR in §2–§3, but solved here via iterative linear algebra rather than a Riccati recursion); (2) solve for the optimal Lagrange multipliers via a custom GPU-parallel PCG solver ("GBD-PCG"), warm-started from the previous control step's solution (§4's warm-start idea, here applied to the linear-system solve itself); (3) run a GPU-parallel line search (simulating *all* candidate step sizes simultaneously, rather than backtracking through them one at a time) to find the final trajectory update.

**Results.** On simulated whole-body end-effector tracking for a Kuka IIWA manipulator (a 5-goal pick-and-place task), MPCGPU's GBD-PCG solver outperformed a state-of-the-art CPU-based sparse linear-system solver (QDLDL) by "at least 10x for a majority of solves and 3.6x on average," with the speedup increasing as trajectory length (number of knot points) grows — from parity at 32 knot points up to a 3.6× average speedup at 512 knot points. The full system scales to trajectories as long as 512 knot points while maintaining kilohertz control rates.

**How it connects.** This paper is a direct, concrete example of the "faster/custom optimizers" MPC speedup named in §4, and its gradient-based nature is the deliberate point of contrast against MPPI/CEM above and against STORM immediately below: modern real-time MPC has two genuinely different GPU-parallelization stories — parallelize the independent sampled rollouts (MPPI/CEM, STORM), or parallelize the linear algebra inside a single gradient-based solve (MPCGPU).

### Paper Breakdown: STORM

*Citation: Mohak Bhardwaj, Balakumar Sundaralingam, Arsalan Mousavian, Nathan Ratliff, Dieter Fox, Fabio Ramos, Byron Boots, "STORM: An Integrated Framework for Fast Joint-Space Model-Predictive Control for Reactive Manipulation," CoRL 2021, arXiv:2104.13542.*

**Problem/motivation.** Classic operational-space control for manipulators is purely local/reactive (it optimizes only the very next action, ignoring future states), while joint-space MPC methods that *do* look ahead have historically been restricted to gradient-based approaches requiring differentiable cost and dynamics — but manipulation tasks routinely involve non-smooth, hard-to-differentiate phenomena like contact, and existing sampling-based (gradient-free) MPC implementations for manipulators had been too slow for real-time, high-dimensional joint-space control.

**Key idea/innovation.** STORM ("Stochastic Tensor Optimization for Robot Motion") is explicitly **MPPI-style sampling-based** MPC — confirming and extending exactly the §6 MPPI derivation above (the paper states its mean-update equation "is the same as the well-known Model-Predictive Path Integral (MPPI) algorithm") — engineered for extreme computational efficiency via batched tensor operations, plus the addition of *adaptive covariance* (updating `Σ_t`, not just `μ_t`, at every iteration, which the paper found improves stability with fewer particles than fixed-covariance MPPI) and low-discrepancy (Halton-sequence) action sampling for smoother, less-noisy sampled trajectories than naive pseudorandom sampling.

**Method & training procedure.** The approximate model used for planning is simply the manipulator's own **kinematic model** (not a learned dynamics model) — joint accelerations `u` are integrated via a batched, fully-parallel tensor operation (no need for a sequential per-timestep simulation loop) to get the full state trajectory across the horizon and the batch of sampled sequences simultaneously, which the paper identifies as key to its low control latency. The cost function is a weighted sum of several batched terms — reaching a target end-effector pose, stopping in time to avoid future collisions given a velocity limit, joint-limit avoidance, avoiding low-manipulability (near-singular) configurations, self-collision avoidance (via a small learned network, "jointNERF," predicting inter-link distance from joint configuration), and environment-collision avoidance (via a separately-learned point-cloud collision classifier) — directly illustrating that a sampling-based planner's cost function can mix hand-designed geometric terms with learned perception components in ways a purely analytic, gradient-based cost function could not as easily accommodate.

**Results.** STORM achieves a control rate of 125 Hz (under 8 ms per control step) on a single GPU — a claimed 100× speedup over prior MPPI-based manipulation implementations. It was validated on a real Franka Panda robot arm across dynamic manipulation tasks including tracking a moving target and balancing a ball on a plate, demonstrating that sampling-based, gradient-free MPC (once properly engineered for GPU parallelism) can control a real, high-dimensional manipulator reactively in real time — directly the capability gap the paper's motivation section identifies as previously unmet.

**How it connects.** STORM is this week's clearest real-hardware confirmation that the MPPI derivation of §6 above is not merely a theoretical construction but the actual algorithm underneath a modern, real-time, real-robot manipulation controller, and its contrast with MPCGPU immediately above gives a concrete, paper-level illustration of the two genuinely different families of GPU-accelerated MPC this week's material spans: independent-rollout (sampling-based) parallelism versus linear-algebra (gradient-based) parallelism.

### Paper Breakdown: End-to-End Differentiable Physics for Learning and Control

*Citation: Filipe de Avila Belbute-Peres, Kevin A. Smith, Kelsey R. Allen, Joshua B. Tenenbaum, J. Zico Kolter, "End-to-End Differentiable Physics for Learning and Control," NeurIPS 2018.*

**Problem/motivation.** Standard physics-simulation environments (MuJoCo, Bullet, and similar) are not natively differentiable, so computing a gradient of anything through them (a policy gradient, a physical-parameter gradient for system identification, a dynamics Jacobian for gradient-based planning) requires finite-differencing — repeatedly re-running the simulator with small perturbations — which is slow (especially with many parameters) and numerically unstable, particularly over long rollouts with changing contacts. This is the *other* possible answer to exactly the gradient-availability problem §6's opening motivated MPPI/CEM as a way to sidestep.

**Key idea/innovation.** Rather than giving up on gradients (as MPPI/CEM do), make the physics engine itself differentiable by deriving *analytic* gradients through the **[linear complementarity problem (LCP)](https://en.wikipedia.org/wiki/Linear_complementarity_problem)** formulation that rigid-body simulators already use internally to resolve contact and friction constraints — this is classical, contact-rich rigid-body mechanics engineered to be compatible with the same backpropagation-based gradient tooling used to train neural networks, not a neural network replacing classical mechanics.

**Method & training procedure.** Rigid-body dynamics with contacts is formulated as a mixed LCP (the standard approach in existing physics engines): at each timestep, the constrained next-step velocities are found by solving a linear system subject to complementarity constraints (contact forces are zero unless bodies are actually touching, and vice versa) — the equality/inequality-constraint matrices are built from the joints, contacts, and friction cone at that step. The LCP is solved via a primal-dual interior-point method (adapting an existing differentiable-QP technique, OptNet, to the more general LCP setting), and — the paper's key technical contribution — the *solution* of this LCP is differentiated analytically with respect to all the LCP's input parameters (masses, positions, contact geometry, etc.), giving exact gradients "for free" from the same forward solve, with no finite-differencing anywhere. The whole engine is implemented as a differentiable PyTorch layer, so it can be embedded inside a larger deep network exactly as any other differentiable module.

**Results.** Three experiment classes: (1) **Parameter learning** — inferring an unknown object's mass purely from observing its dynamical interactions (a ball of known mass colliding with a chain of unknown mass); gradient descent on the mass parameter converges quickly to the true value, and the analytic-gradient approach's runtime scales far better with the number of parameters than a finite-differencing baseline (which becomes far slower as the number of chain links grows). (2) **Visual prediction** — an autoencoder architecture with the differentiable physics engine embedded as its "predict" step between encoder and decoder, trained on billiard-ball-style videos; using unlabeled data alongside the physics-engine layer improved sample efficiency compared to a supervised-only baseline, and the model produced qualitatively accurate predicted future frames. (3) **Control** — the differentiable model is combined with **iLQR** (explicitly citing Li & Todorov's iLQR, §3's own Paper Breakdown above, as the planner used) for gradient-based trajectory optimization on Cartpole and the Atari game Breakout; on Cartpole, the physics-engine-based controller reached near-maximum reward (up to the environment's 1000-reward cap) very quickly, even though a plain MLP baseline model achieved *lower* one-step prediction MSE — a direct illustration that being good at predicting the next state and being good enough for control are not the same thing (a theme returned to more formally in §8's value-aware model learning). On Breakout, the physics-based controller reached a reward around 400 (comfortably above the human-level baseline of 31 reported by Mnih et al. 2015) using orders of magnitude fewer environment samples than a Double Q-Learning model-free baseline, though the model-free baseline eventually reached somewhat higher asymptotic reward given far more data.

**How it connects.** This paper is the primary concrete anchor for framing question (3) — **how does optimal control relate to neural networks?** — previewed here and fully answered in §9.3: it is not "classical mechanics versus neural networks" but classical, contact-rich mechanics *made compatible with* neural-network-style gradient tooling, so that a classical planner (iLQR, §3) can be run through it exactly as it would through any other differentiable model. It directly complements §6's sampling-based MPPI/CEM as the *other* available fix to the same gradient-availability problem: make the model differentiable, rather than avoid needing its gradient at all.

## 7. Model-based RL in practice — anchoring the loop with real systems

§5's model-based RL loop (collect, fit, plan, execute, repeat) is a general recipe; this section anchors it with real systems, real robots, and real numbers, moving roughly from the smallest, most sample-efficient methods to the most visually/architecturally rich one (PlaNet).

### Paper Breakdown: PILCO

*Citation: Marc Peter Deisenroth, Carl Edward Rasmussen, "PILCO: A Model-Based and Data-Efficient Approach to Policy Search," ICML 2011.*

**Problem/motivation.** Standard reinforcement learning is extremely data-inefficient — the paper notes that even a simple task like mountain-car can require "tens if not hundreds or thousands of trials" for model-free methods. Model-based approaches promise better data efficiency by reusing a learned dynamics model across many planning iterations instead of needing fresh real-world trials for every policy update, but naive model-based RL suffers from **model bias**: a deterministic learned model, once queried outside the region it was trained on, can diverge wildly from reality while reporting its prediction with full (false) confidence — silently compounding exactly the kind of model error §5's multi-step-prediction discussion and §8's compounding-error discussion address from different angles.

**Key idea/innovation.** PILCO — "**p**robabilistic **i**nference for **l**earning **co**ntrol," which is also literally where the algorithm's name comes from — combines three pieces: a **[Gaussian Process (GP)](https://en.wikipedia.org/wiki/Gaussian_process)** dynamics model that reports calibrated *uncertainty* about its own predictions rather than a single deterministic guess (directly counteracting the model-bias problem above, since the model now says explicitly where it doesn't know); **[moment matching](https://en.wikipedia.org/wiki/Moment_(mathematics))** to propagate that uncertainty forward through a multi-step rollout in closed form; and fully **analytic policy gradients** computed through the entire moment-matching chain, with no sampling anywhere in the gradient computation.

**Method & training procedure.** The GP is trained on inputs `(x_{t-1}, u_{t-1})` to predict `Δ_t = x_t - x_{t-1} + ε` (exactly §5(b)'s "predict `Δx` instead of the next state" refinement, with `ε` an explicit noise term), using a squared-exponential kernel with automatic relevance determination (ARD, meaning the kernel learns a separate lengthscale per input dimension, which effectively performs feature-relevance weighting on the input state/action space). Because propagating a distribution exactly through a nonlinear GP is intractable in closed form, PILCO uses moment matching: at each rollout step, the true (intractable) predictive distribution over the next state is *approximated* by a Gaussian with an *exactly computed* mean and variance (both available in closed form via known kernel-expectation integrals for the squared-exponential kernel), and this Gaussian approximation is what gets fed forward as the input state distribution to the next step's GP prediction — so uncertainty compounds and grows across the rollout in a mathematically explicit, trackable way, rather than being silently discarded. Because every one of these steps is differentiable in closed form, the policy gradient `dJ/dθ` is computed by the chain rule straight through the entire moment-matching recursion, with no Monte Carlo sampling anywhere — the paper explicitly motivates this by noting that "the variance in the gradient estimate grows quickly with the number of parameters" for sampling-based policy-gradient alternatives. The cost function `c(x) = 1 - exp(-‖x - x_target‖² / σ_c²) ∈ [0, 1]` is chosen specifically because its expectation under a Gaussian state distribution is also available in closed form, keeping the entire pipeline analytically tractable end to end.

**Results.** On a real physical cart-pole swing-up task, PILCO solved the task using only **17.5 seconds of total real-world interaction** (per the paper's Figure 3 caption), with Table 1 separately reporting "≈20s" for the same task (the two numbers are both given in the paper and are not reconciled here). A cart-double-pendulum swing-up task required roughly 20–30 trials (60–90 seconds of interaction). A 12-dimensional-state unicycle-riding task needed only about 20 trials (~30 seconds of interaction) and reached a 93% success rate over 1000 independent test rollouts. The paper claims PILCO "outperforms any other algorithm by at least one order of magnitude" on cart-pole data efficiency against named prior model-free methods. A robustness check — shrinking the cost function's width parameter `σ_c` down to `1e-6` meters — still succeeded, which the paper uses to argue the method's efficiency isn't merely an artifact of generous reward shaping.

**How it connects.** PILCO is the clearest concrete instance of §5's "predict `Δx`" refinement and §5's general model-based RL loop, run with a GP as the world model and moment matching plus analytic gradients as the planning step (in place of §6's sampling-based CEM/MPPI or §2–§3's LQR/iLQR). Its uncertainty-aware GP dynamics model is also the direct conceptual ancestor of PETS' uncertainty-aware ensemble below, which replaces PILCO's GP (elegant but computationally expensive at scale) with a scalable neural-network alternative.

### Paper Breakdown: Synthesizing Neural Network Controllers with Probabilistic Model-Based RL (Gamboa Higuera, Meger & Dudek)

*Citation: Juan Camilo Gamboa Higuera, David Meger, Gregory Dudek, "Synthesizing Neural Network Controllers with Probabilistic Model Based Reinforcement Learning," IROS 2018, arXiv:1803.02291.*

**Problem/motivation.** PILCO's GP dynamics model scales poorly — cubically in the number of training points for fitting, worse for long-term prediction — restricting it to small, low-dimensional problems. Deep-PILCO, an earlier attempt to replace PILCO's GP with a Bayesian neural network, reduced data efficiency compared to the original PILCO.

**Key idea/innovation.** Bayesian neural network dynamics models trained with a specific, calibrated form of **multiplicative dropout noise** (truncated Log-Normal, contrasted explicitly against plain binary dropout in the paper), combined with two further fixes needed to make gradient-based policy optimization through the resulting stochastic rollout actually work: **common random numbers** (fixing the random seeds used within one optimization run rather than resampling them at every gradient step, which the paper found stabilized convergence, at the cost of needing more particles — 100 instead of Deep-PILCO's 10 — to keep the resulting gradient estimate well-behaved) and **gradient clipping** (to stabilize backpropagation-through-time through the long unrolled particle-based rollout, since — unlike PILCO's closed-form analytic GP gradients — a neural-network dynamics model has no closed-form gradient chain and must be backpropagated through numerically).

**Method & training procedure.** The dynamics model is a ReLU MLP (2 hidden layers of 200 units for cart-pole; 4 hidden layers of 200 units for the harder double-cart-pole and underwater-vehicle tasks) predicting `Δ_t` with heteroscedastic (state-dependent) noise. Uncertainty is propagated by simulating `K` particles forward, each through an independently-sampled instance of the dropout-based BNN, then Gaussian-moment-matching the resulting particle population back together at each timestep before resampling for the next step — a hybrid of PILCO's moment matching and an explicit particle representation, rather than pure GP moment matching. The policy itself is also a dropout-based BNN (resampled at every timestep, providing built-in stochastic exploration), optimized end-to-end via Adam on gradients obtained by backpropagation-through-time through the entire particle-based rollout.

**Results.** Deployed on a simulated model of the AQUA underwater hexapod robot (the simulation environment itself drawn from prior ICRA 2015 hardware work, not open-water testing) across four swimming/depth-control tasks. Tasks using 2 legs (4 control dimensions) converged within 10–20 trials; tasks using all 6 legs (18 control dimensions) took roughly double that, converging by trial 50 — and the depth-change task succeeded here where prior model-free work on the same platform had failed outright. On the standard cart-pole/double-cart-pole benchmarks, the method matched PILCO's data efficiency while reaching a better final cost; the double-cart-pole task converged at 42 trials (126 seconds of simulated interaction), compared to a figure of 84 seconds at 13.3 Hz reported in Deisenroth's PILCO-era thesis work.

**How it connects.** This paper is the direct bridge between PILCO's GP-based world model and PETS' neural-network-ensemble world model immediately below — same uncertainty-aware modeling philosophy (don't trust a single deterministic dynamics prediction), same moment-matching-flavored uncertainty propagation, but scaled up via a Bayesian neural network to problems (an 18-dimensional control space) well beyond what a GP-based approach like PILCO could practically handle.

### Paper Breakdown: PETS (Probabilistic Ensembles with Trajectory Sampling)

*Citation: Kurtland Chua, Roberto Calandra, Rowan McAllister, Sergey Levine, "Deep Reinforcement Learning in a Handful of Trials using Probabilistic Dynamics Models," NeurIPS 2018, arXiv:1805.12114.*

**Problem/motivation.** Model-based RL is sample-efficient but has historically lagged model-free RL's asymptotic (long-run) performance, and this gap becomes especially pronounced when the dynamics model is a high-capacity deep neural network rather than a GP.

**Key idea/innovation.** "**P**robabilistic **e**nsembles with **t**rajectory **s**ampling" (PETS) combines two genuinely distinct sources of uncertainty in one system: **[aleatoric uncertainty](https://en.wikipedia.org/wiki/Uncertainty_quantification)** (inherent randomness in the environment itself, captured by having each network output a full Gaussian mean-and-variance prediction rather than a single point estimate) and **[epistemic uncertainty](https://en.wikipedia.org/wiki/Uncertainty_quantification)** (uncertainty due to limited training data, captured by an **ensemble** of `B = 5` independently, bootstrap-trained networks) — the paper's own Table 1 confirms this "probabilistic ensemble" combination is the only one of its tested model variants capturing both uncertainty types simultaneously.

**Method & training procedure.** The planner is explicitly **[CEM](https://en.wikipedia.org/wiki/Cross-entropy_method)** (§6 above) — not the simpler random-shooting baseline used by prior work, which the paper explicitly improves on ("we use CEM instead of random-shooting... samples actions from a distribution closer to previous action samples that yielded high reward") — run inside an outer MPC replanning loop (§4), following the algorithmic shape `for actions sampled from CEM: ... update the CEM distribution`. Uncertainty propagation through the ensemble is done via **Trajectory Sampling (TS)**: `P = 20` particles are propagated per candidate action sequence, each particle following one of the `B = 5` bootstrapped ensemble members; two variants are compared — **TS1** (each particle re-samples which bootstrap member it follows at *every* timestep) and **TS∞** (each particle keeps the *same* bootstrap member for the entire rollout, which lets aleatoric and epistemic uncertainty be attributed and separated more cleanly, since within-particle variation across a TS∞ rollout is purely aleatoric while across-particle variation is purely epistemic).

**Results.** PETS reaches the same asymptotic performance as Soft Actor-Critic and Proximal Policy Optimization using "8 and 125 times fewer samples... respectively on the half-cheetah task." Across four tested environments (Cartpole, a 7-DOF Pusher, a 7-DOF Reacher, and Half-cheetah), PETS "learns in under 100K time steps or 100 trials" on all four, reaching PPO's asymptotic performance faster than any prior model-free algorithm tested on all four, and substantially outperforming a prior deterministic model-based baseline (Nagabandi et al. 2017). A GP-based baseline (GP-MM, i.e. essentially PILCO-style moment matching) slightly outperformed PETS on Cartpole alone, but the paper notes it scales cubically in the number of training points and quadratically in state dimension, making it infeasible on the higher-dimensional tasks where PETS still succeeds. Ablating the model type gives a clean ranking: probabilistic ensemble (PE) > plain probabilistic single network (P) > deterministic ensemble (DE) > plain deterministic single network (D) — directly confirming both ingredients (probabilistic outputs *and* ensembling) contribute independently. Notably, the paper explicitly reports a *negative* result: directly backpropagating policy gradients through the uncertainty-aware model did not work well in their experiments, possibly due to "chaotic policy gradients" — motivating the CEM-based, gradient-free planning approach used instead.

**How it connects.** PETS is this week's cleanest direct instantiation of §6's CEM inside §4's MPC loop, run on top of §5's model-based RL loop with an ensemble-of-neural-networks world model — connecting three separate pieces of this week's machinery (§4, §5, §6) into one concrete, well-benchmarked system, and its ensemble-uncertainty philosophy is the direct ancestor of MBPO's (§8) use of a model ensemble as well.

### Paper Breakdown: DPI-Nets (Dynamic Particle Interaction Networks)

*Citation: Yunzhu Li, Jiajun Wu, Russ Tedrake, Joshua B. Tenenbaum, Antonio Torralba, "Learning Particle Dynamics for Manipulating Rigid Bodies, Deformable Objects, and Fluids," ICLR 2019, arXiv:1810.01566.*

**Problem/motivation.** Rigid bodies, deformable objects, and fluids all have qualitatively different dynamics; hand-designed physics simulators built for graphics realism (rather than true physical accuracy) can deviate substantially from real-world physics over long planning horizons, and there was previously no single learned model generalizing across all three material types for manipulation planning.

**Key idea/innovation.** **Dynamic Particle Interaction Networks (DPI-Nets)** extend prior "Interaction Networks" (a graph-neural-network-style architecture for learned physics simulation) with two innovations: **dynamically-rebuilt graphs**, where edges connect only particles within some distance threshold and the graph is rebuilt from scratch at every simulated step (needed because many physical interactions, especially contact, are inherently discontinuous — an edge either exists or doesn't depending on current proximity — which a static or fully-connected graph cannot represent efficiently); and a **hierarchical clustering scheme** specifically for rigid bodies, where particles are grouped into clusters each represented by a synthetic "root" particle, so that information can propagate leaf → root → root → leaf in only a few message-passing rounds instead of needing many rounds of purely local, particle-to-particle message passing to coordinate motion across an entire rigid object.

**Method & training procedure.** Object and relation encoders feed a multi-step propagation-network architecture (message passing repeated for several rounds per simulated timestep) predicting each particle's next state, with material-specific output heads: rigid bodies average the hierarchical signal into one rigid-body transform applied to the whole object; deformable (elastic/plastic) materials predict per-particle position and "resting position" updates; fluids need no hierarchy and use purely local neighbor-based propagation. Because the learned model is an ordinary differentiable neural network, its rollouts support **gradient-based shooting-method trajectory optimization** for control: sample many random candidate control sequences, pick the best-scoring one as an initialization, then refine it further via gradient descent through the learned model — with **MPC** replanning (§4) and **online system identification** (adjusting unknown physical parameters like mass or stiffness via SGD, on the fly, during execution) added for robustness at deployment time.

**Results.** Across four simulated benchmark environments (FluidFall, BoxBath, FluidShake, RiceGrip), DPI-Nets achieved lower forward-simulation mean-squared error than both plain Interaction Networks and a prior hierarchical baseline (HRN) — e.g. on RiceGrip, DPI-Net reached `0.13 ± 0.07` (×10⁻²) MSE versus HRN's `0.17 ± 0.11`; plain (non-hierarchical, non-dynamic-graph) Interaction Networks ran out of 12GB of GPU memory on every environment except the very simplest, since its fully-connected graph representation doesn't scale. On control, the full pipeline (random-search initialization plus gradient-based trajectory optimization plus online system identification) substantially outperformed both a model-free PPO baseline and a random-search-only ablation, using roughly 150K environment timesteps versus PPO's roughly 10M in one reported comparison — a dramatic sample-efficiency gap. The full system was demonstrated on a real Kuka robot arm manipulating deformable foam into target shapes, using depth-camera-reconstructed particle geometry as the observed state, and successfully adapted to unknown real physical parameters via the online system-identification component.

**How it connects.** DPI-Nets is this week's richest example of §5's world-model idea applied to genuinely difficult material types (deformables, fluids) that classical, hand-derived dynamics (§2–§3's linear/nonlinear rigid-body models) simply cannot capture, and its gradient-based shooting-plus-MPC control pipeline is a second concrete instance (alongside §6's differentiable-physics Paper Breakdown) of pairing a learned, differentiable world model with classical trajectory optimization rather than replacing optimization with a learned policy outright.

### Paper Breakdown: DeepMPC

*Citation: Ian Lenz, Ross A. Knepper, Ashutosh Saxena, "DeepMPC: Learning Deep Latent Features for Model Predictive Control," RSS 2015.*

**Problem/motivation.** Robotic food-cutting is a concrete, hard instance of §5's "even known physics is hard for real robots" theme: cutting dynamics depend on hard-to-model material properties (friction, elastic modulus, fracture and hysteretic effects) that vary both *across* material classes (butter versus a lemon) and *within* a single piece of material over time as the knife moves from skin to flesh — designing a hand-built dynamics model, or even a hand-built set of material-property features, for this task is essentially infeasible.

**Key idea/innovation.** Rather than hand-designing a dynamics model or a fixed set of material-property features, learn a deep recurrent dynamics model whose **latent features implicitly represent material properties**, trained end-to-end for receding-horizon prediction, and plug that learned, differentiable model directly into an online, real-time MPC controller (§4's replanning loop).

**Method & training procedure.** The predictive model, novel to this paper, uses **multiplicative conditional interactions** (factored units whose output depends on the *product*, not just the sum, of two input feature groups — letting the model blend between very different local dynamics models depending on which features are currently active, analogous to a soft, learned mixture-of-experts-like gating) and **temporal recurrence** via what the paper calls "transforming recurrent units" (TRUs), which carry latent state forward across time-blocks to capture slowly-varying properties like which material is currently being cut, distinct from the fast, block-local dynamic response to the immediate control input. Training uses a specific three-stage procedure to avoid the instability and "exploding gradient" problems common when training deep recurrent networks from a random initialization: (1) **unsupervised pre-training** of the non-recurrent latent-feature weights via a sparse-autoencoder-style reconstruction objective; (2) **short-term (single-step) prediction training**, with recurrent weights temporarily zeroed out, to get accurate one-step dynamics before letting information flow across time; (3) **warm-latent recurrent training**, which finally trains the full recurrent multi-step prediction system (with a backpropagation-through-time variant), including a deliberate "warm-up" period where the model is allowed to build up latent state without being penalized for early prediction error, so it isn't forced to make confident predictions from a cold, uninformative initial latent state. Because the whole model is differentiable, the online controller computes gradients of a hand-designed MPC cost function (penalizing knife height for a cutting-progress term, and a term keeping the sawing motion within a valid range along the blade) with respect to future control forces, and optimizes them online via AdaGrad — reported to run at over 1.2 kHz on a PR2 robot.

**Results.** On an offline prediction benchmark (1488 examples of robotic cutting across 20 diverse food materials), the full DeepMPC model achieved substantially lower mean prediction error (1.78 mm at a 0.5-second horizon) than a non-recurrent version of the same architecture (3.80 mm), a plain two-layer non-recurrent deep network baseline (4.90 mm), and even a Gaussian Process baseline (3.56 mm, but requiring roughly 3361 seconds — about 56 minutes — to predict 0.5 seconds ahead, some 1.18 million times slower than DeepMPC's 3.1 ms). The careful pre-training procedure mattered concretely: a randomly-initialized version of the same recurrent architecture gave 2.78 mm error, meaning the full pre-training pipeline reduced error by roughly 36% relative to random initialization and roughly 46% relative to the non-recurrent baseline. In over 450 real-world robotic cutting trials on a PR2 with a knife-wielding gripper, DeepMPC's online controller significantly improved cutting rate over both a class-generic and (for most materials) even class-*specific*, hand-tuned stiffness controller: for the four hardest materials tested (lemons, potatoes, carrots, apples), the learned controller more than tripled the mean cutting rate, from 1.5 cm/s (best stiffness-control baseline) to 5.1 cm/s — with lemons improving from 1.3 to 4.5 cm/s and apples from 1.4 to 4.6 cm/s specifically. The controller was also observed to discover qualitatively diverse cutting strategies unavailable to a fixed-trajectory stiffness controller, including varying sawing amplitude, using "wiggle" motions, and briefly lifting and re-applying the knife to break static friction on tough materials.

**How it connects.** DeepMPC is a direct, real-robot instance of §5's model-based RL loop's "fit a differentiable world model, then plan through it" pattern, using gradient-based online optimization (rather than §6's gradient-free CEM/MPPI) exactly as iLQR/MPC (§3–§4) would, but with a learned, materials-aware recurrent dynamics model in place of a hand-derived one — and its latent, implicitly-inferred material-property features are a direct predecessor, in spirit, of PlaNet's learned latent state immediately below.

### PlaNet's Recurrent State-Space Model — a genuinely new architecture, built bottom-up

PlaNet (below) introduces a network architecture — the **[Recurrent State-Space Model (RSSM)](https://en.wikipedia.org/wiki/State-space_representation)** — that is a meaningfully new departure from anything covered in Week 1 or earlier this week, and it earns the same from-scratch, bottom-up treatment those notes give any other unfamiliar architecture.

**Plain-language analogy for "recurrent."** Imagine reading a novel one page at a time versus re-reading the entire book from page one every time you want to know what's currently happening. A **recurrent** network is the first kind of reader: it carries forward a compact running summary ("what's happened in the story so far") and updates that summary incrementally, one new page (timestep) at a time, rather than reprocessing the entire history from scratch at every step. This "running summary" is exactly what an RNN's hidden state represents, applied here to a robot's continuously-arriving stream of camera images and actions instead of a stream of pages.

**Plain-language analogy for latent stochastic state.** Rather than directly predicting the *next camera image* (a huge, high-dimensional, pixel-level object), predict a much smaller, compact, unobserved ("latent") summary vector describing the scene's state, and only decode that summary into an actual image or reward when one is actually needed (for training, or for a human to inspect) — much like keeping a compact mental summary of a scene ("the ball is falling, about to hit the cart") rather than a full photographic memory of every pixel. This latent summary is treated as genuinely *uncertain* (a probability distribution, not a single fixed vector) because a single raw image frequently doesn't disambiguate everything relevant — e.g. a static image alone cannot reveal an object's *velocity*, only a sequence of images can, so right after a new image arrives there may still be real ambiguity about the full physical state that a probabilistic latent variable can represent honestly.

**Structure.** The RSSM has four connected pieces, moving from the familiar to the unfamiliar:
1. A **CNN encoder** (entirely familiar from Week 1) maps a raw camera image into an intermediate feature representation.
2. A **deterministic recurrent path** `h_t = f(h_{t-1}, s_{t-1}, a_{t-1})`, implemented as an RNN, carries forward a running summary of everything seen and done so far — the "reading one page at a time" mechanism above, letting the model remember information across many timesteps.
3. A **stochastic latent state** `s_t`, combining the deterministic hidden state `h_t` with the current encoded observation (during training) into a probability distribution over the "true" current latent state — this is the piece that lets the model represent genuine uncertainty/multiple plausible current states, rather than committing to one deterministic guess.
4. A **learned transition model** `p(s_t | h_t)` — critically, predicting the next stochastic state from the current deterministic hidden state and action **without access to the next actual observation**. This is exactly what makes the model usable for *planning*: at planning time there is no future image to peek at, so the model must be able to predict forward "blind," using only what it already knows plus the hypothetical action being considered.
5. **Decoder heads** (a deconvolutional network reconstructing images, plus a small feedforward network predicting rewards) reconstruct observable quantities from the latent state — used during training to supply a learning signal, and optional at planning time (planning can run entirely in the compact latent space, using only the reward head, without ever generating an actual image).

**Input / output / label / loss.** Input: a sequence of (image, action) pairs collected from real interaction. Output: reconstructed images, predicted rewards, and predicted future latent states. There is no separate "label" beyond the real observations and rewards actually experienced — training is self-supervised in the same sense an autoencoder is. The loss (a variational bound on the data log-likelihood, in the same broad family as a variational autoencoder's loss) combines an image-reconstruction term, a reward-prediction term, and — the piece specific to this architecture's own key design decision — a **consistency term** between the "blind" transition-model prediction (piece 4 above, predicting `s_t` from only `h_t`, with no access to the current image) and the "informed" posterior latent state (piece 3, which *does* see the current image): the model is trained so that what it can predict blind stays close to what it would infer if it were allowed to peek at the answer. This consistency loss is exactly what makes the "blind" transition model trustworthy enough to use for multi-step planning later, since during training it's continually being pulled toward matching what an "informed" pass would have concluded.

**What's genuinely innovative, contrasted against everything covered so far.** An ordinary regression-head CNN policy (Week 1, §2) predicts an action *directly* — "predict-directly." An energy-based policy (Week 1, §7.3) instead *evaluates* candidate actions and searches for the best one — "evaluate-and-search." PlaNet's RSSM does **neither**: it doesn't predict an action or evaluate one at all — instead it **compresses observations into a small latent space and learns to simulate forward within that compressed space**, so that any of §2–§6's planners (PlaNet specifically uses CEM, §6) can run entirely on cheap, compact latent-state rollouts instead of on expensive, high-dimensional raw pixels. This is a "compress-and-simulate-forward" design — directly instantiating §5's "world model" idea, but with the added twist that the learned world model operates over a *learned, compact* latent state rather than the raw observation space.

### Paper Breakdown: PlaNet (Learning Latent Dynamics for Planning from Pixels)

*Citation: Danijar Hafner, Timothy Lillicrap, Ian Fischer, Ruben Villegas, David Ha, Honglak Lee, James Davidson, "Learning Latent Dynamics for Planning from Pixels," ICML 2019, arXiv:1811.04551.*

**Problem/motivation.** Planning is a powerful, well-understood approach when the dynamics are known exactly (§2–§4), but learning a dynamics model accurate enough to plan through, directly from raw pixel observations, has been a long-standing challenge: errors compound over multi-step predictions (exactly §5's compounding-error theme), a model may fail to represent multiple genuinely possible futures, and models can become badly overconfident on inputs outside their training distribution (echoing PILCO's model-bias concern above).

**Key idea/innovation.** The RSSM architecture detailed above, plus a training objective called **latent overshooting** — a generalization of the standard one-step-ahead variational training objective to *also* train the model's multi-step latent predictions directly (not merely as an emergent side effect of chaining one-step predictions together), which the paper found improves the model's usefulness for long-horizon planning specifically. The paper explicitly highlights, as one of its own two central findings, that *both* the deterministic and stochastic parts of the RSSM are necessary for successful planning — an ablation confirms a purely deterministic (GRU-only) model can't represent multiple futures, while a purely stochastic (state-space-model-only) model struggles to remember information across many timesteps, and the two together are needed.

**Method & training procedure.** The RSSM (as detailed above) is trained on sequences of images/actions/rewards from the six DeepMind control suite tasks shown in the paper's Figure 1 (Cartpole swing-up, Reacher, Cheetah running, Finger spinning, Cup catching, Walker) — chosen specifically because they cover qualitatively different difficulties: a long planning horizon (Cartpole), sparse reward (Reacher, Cup), contact dynamics and many joints (Cheetah), and needing to first stand up before walking (Walker). At each real-environment timestep, the agent infers its current latent-state belief via the encoder, plans forward using **[CEM](https://en.wikipedia.org/wiki/Cross-entropy_method)** (§6 above) entirely in latent space (since the reward head can be evaluated on latent states directly, without ever decoding back to images during planning — this is precisely why PlaNet needs the reward head as a distinct, separately-trained output), executes the first action of the resulting plan (§4's MPC loop, again), and appends the newly observed real transition to the training data.

**Results.** Within under 100 episodes, PlaNet already outperforms the model-free policy-gradient algorithm A3C trained on proprioceptive (non-image) state for 100,000 episodes, on all six tasks. After 500 episodes, PlaNet achieves performance similar to the strong model-free algorithm D4PG trained from images for 100,000 episodes, on all tasks except Finger; on Cheetah running specifically, PlaNet's final performance exceeds D4PG's by a reported 26% relative improvement. The paper's own Table 1 reports the estimated data-efficiency gain of PlaNet over D4PG per task (episodes needed by D4PG to match PlaNet's performance, divided by PlaNet's own episode count): roughly 250× (Cartpole Swing Up), 40× (Reacher Easy), 500+× (Cheetah Run), 300× (Finger Spin), 100× (Cup Catch), and 90× (Walker Walk) — averaging to the headline claim (from the paper's abstract) of "on average 200× less environment interaction" than the strong model-free baseline, at similar computation time. A separate ablation (Figure 4) directly confirms the "why the RSSM's structure matters" claim above: PlaNet's full RSSM clearly outperforms both purely-deterministic (GRU) and purely-stochastic (SSM) alternatives on every task tested.

**How it connects.** PlaNet is this week's concrete confirmation of §5's "world model = learned dynamics model, possibly over a learned latent state" framing, and its RSSM architecture — genuinely new relative to anything in Week 1 — is treated with full bottom-up architectural depth immediately above precisely because, per this project's own standards, naming a novel architecture and glossing what it does is not sufficient; contrast its "compress-and-simulate-forward" design explicitly against Week 1's predict-directly (regression) and evaluate-and-search (energy-based) policy designs, both described above. PlaNet's planner of choice, CEM, is the exact algorithm derived in §6, run here inside the RSSM's compact latent space rather than over raw pixels or a low-dimensional hand-specified state.

### Reading write-up: Chatzilygeroudis et al., "A Survey on Policy Search Algorithms for Learning Robot Controllers in a Handful of Trials"

*Citation: Konstantinos Chatzilygeroudis, Vassilis Vassiliades, Freek Stulp, Sylvain Calinon, Jean-Baptiste Mouret, "A Survey on Policy Search Algorithms for Learning Robot Controllers in a Handful of Trials," IEEE Transactions on Robotics, 2019, arXiv:1807.02303.*

**Survey scope.** This survey addresses what it calls **"micro-data" reinforcement learning** — enabling a real robot to learn a good controller using only "a handful of trials (a dozen) and a few minutes" of real-world interaction, rather than the thousands of episodes standard policy-search algorithms typically require. It organizes the (large) literature of methods achieving this by identifying two broad strategies that, in the survey's own words, "all successful micro-data algorithms combine... by varying the kind of model and prior knowledge": **leveraging prior knowledge** (structuring the policy itself around known primitives, initializing policy parameters from demonstrations, or building in a known simulator/approximate model of the dynamics) and **surrogate modeling** (fitting a data-driven model — a reward model via Bayesian optimization, or a dynamics model enabling model-based policy search of exactly the kind derived throughout this week) to reduce how many expensive real-robot queries are needed.

**Taxonomy/conclusions.** The survey's taxonomy places methods like PILCO (above) squarely in the "learn a dynamics model, then do model-based policy search" family, while noting the field's central open challenges are scaling these methods to more complex, higher-dimensional robots (e.g. humanoids), designing priors general enough to transfer usefully across different tasks rather than being hand-tuned per task, and reducing the computational cost of the (often expensive) model-fitting and planning steps themselves.

**How it connects.** This survey is a direct, higher-level companion to PILCO and the Gamboa Higuera et al. paper above, both of which are exactly "micro-data" policy-search methods in this survey's own sense, and its "prior knowledge plus surrogate modeling" taxonomy is a useful lens for classifying essentially every model-based method covered in this section: PETS and DPI-Nets both use a learned surrogate dynamics model; DeepMPC and PlaNet both additionally bring in a hand-designed cost/reward structure (prior knowledge) layered on top of their learned models.

### Reading write-up: Kober, Bagnell & Peters, "Reinforcement Learning in Robotics: A Survey"

*Citation: Jens Kober, J. Andrew Bagnell, Jan Peters, "Reinforcement Learning in Robotics: A Survey," International Journal of Robotics Research (IJRR), 32(11), 2013.*

**Survey scope.** A broad survey of reinforcement learning applied to robot behavior generation, organized primarily along two axes the paper treats as its central design choices: **value-function-based** versus **policy-search** methods, and **model-based** versus **model-free** approaches — precisely the model-based/model-free distinction this week's entire set of notes has been developing (§5's "learn `f_θ`, then plan through it" being the model-based side; a policy or value function fit directly from experience with no explicit dynamics model, as in much of Week 1's BC/DAgger machinery once reward rather than expert-action supervision is involved, being closer to the model-free side). The survey explicitly situates imitation learning and reinforcement learning relative to ordinary supervised learning along a "complexity of sequential interaction" axis (Figure 2 of the paper): supervised learning sits at one extreme (no interaction — training and test data are i.i.d.), imitation learning sits further along that axis because "any mistake by the learner modifies the future observations from what would have been seen had the expert chosen the controls" (exactly Week 1's covariate-shift argument, §3.2 of `week1-study-notes.md`, restated here in this survey's own words), and full reinforcement learning sits furthest along the same axis, additionally handling reward structures more complex than imitation's implicit "match the expert" signal.

**Main takeaway/argument.** The survey identifies robotics-specific challenges that distinguish robot RL from RL in general: the **curse of dimensionality** in realistic robots' continuous, high-dimensional state/action spaces; the sheer cost of collecting real-world robot experience compared to a simulator (motivating exactly this week's emphasis on model-based, sample-efficient methods); and the importance of incorporating prior structure and knowledge (analogous to Chatzilygeroudis et al.'s "leveraging prior knowledge" strategy above) to make learning tractable at all on physical hardware. Its running illustrative example is table-tennis ball-return, framed explicitly in MDP terms (ball/racket state, torque or acceleration actions, a policy mapping observations to motor commands) to demonstrate how a real robotics problem maps onto the standard RL formalism.

**How it connects.** This survey's model-based/model-free and value-function/policy-search taxonomy is the RL-side complement to Chatzilygeroudis et al.'s policy-search-specific survey above, and its explicit callout of imitation learning's covariate-shift problem — described independently, in the same terms, as Week 1's own treatment — is a useful confirmation that this project's Week 1 framing matches how the broader field itself describes the same phenomenon.

## 8. Trusting the model: monotonic improvement and value-aware learning

Every model-based method so far (§5–§7) plans through a learned model `f_θ` that is, inevitably, imperfect. This raises an obvious and important question that none of the Paper Breakdowns above answer rigorously: **if `f_θ` is wrong, does improving the policy's performance *under the model* actually guarantee any improvement in the policy's performance on the *real* system?** Without an answer, "improving under the model" could in principle just mean "getting better at exploiting the model's own blind spots" — a policy that looks great in simulation but fails in reality.

**Building the argument in plain language, before any formulas.** Suppose it's possible to compute a number — call it a **guaranteed lower bound** — on the real-world performance of a policy, using only quantities available under the model (the model's predicted performance, minus some penalty capturing how much the model might be wrong). If, at every iteration of training, the algorithm is required to *improve this lower bound* (not just the model-predicted performance, which could be gamed by exploiting model error), then because the bound is a genuine lower bound on real performance, real performance must be at least as good as what the bound says — so improving the bound guarantees the real system's performance goes up too, monotonically, iteration after iteration. This "improve a provable lower bound, not the possibly-gameable raw model score" pattern is the shared idea underneath both papers below.

### Paper Breakdown: SLBO (Stochastic Lower Bounds Optimization)

*Citation: Yuping Luo, Huazhe Xu, Yuanzhi Li, Yuandong Tian, Trevor Darrell, Tengyu Ma, "Algorithmic Framework for Model-Based Deep Reinforcement Learning with Theoretical Guarantees," ICLR 2019, arXiv:1807.03858.*

**Problem/motivation.** Despite model-based RL's promising empirical sample-efficiency gains, its theoretical properties are poorly understood: does model error provably bound how far off the resulting policy can be? Can a model-based algorithm be guaranteed to improve the policy monotonically, converging to at least a local optimum, the way certain model-free policy-gradient methods (e.g. TRPO) can be shown to?

**Key idea/innovation.** A meta-algorithm that, at every iteration, constructs an explicit, provable **lower bound** on the policy's true (real-environment) value, `V^{π,M*} ≥ V^{π,M̂} - D(M̂, π)`, where `V^{π,M̂}` is the value estimated under the current learned model `M̂` and `D(M̂, π)` is a **discrepancy bound** quantifying how much the model and the real environment could plausibly differ — then jointly optimizes this lower bound over *both* the policy and the model parameters simultaneously. Crucially, this extends the classical "optimism in the face of uncertainty" principle (well-established for simple, finite-state problems) to deep, nonlinear dynamics models **without requiring any explicit uncertainty quantification** (no confidence intervals, no ensemble, no Bayesian posterior over the model) — the discrepancy bound is instead derived directly from how model-prediction error is expected to affect the value function, sidestepping the (very hard, still largely open) problem of getting calibrated uncertainty estimates out of an arbitrary deep network.

**Method & training procedure.** The meta-algorithm (their Algorithm 1) iterates: given the current policy `π_k`, jointly optimize the policy and model to maximize `V^{π,M} - D_{π_k}(M, π)` subject to the new policy staying within a bounded distance `δ` of the reference policy `π_k` (a trust-region-style constraint, in the same spirit as §3's trust-region safeguard on iLQR, here bounding how far the *policy* can move rather than how far a *trajectory* can move). The paper proves (Theorem 3.1) that, as long as this per-iteration optimization is solved successfully, the resulting sequence of policies has **monotonically non-decreasing true value** — a formal proof of exactly the plain-language argument given above — and separately shows the sequence converges to a local maximum of the true value function. The practical instantiated algorithm, **SLBO**, simplifies the general framework: it drops the explicit trust-region constraint, stops the gradient with respect to the model (but not the policy) when computing the value term, and — motivated directly by the paper's own theoretical analysis, which favors a norm over a squared norm — trains the dynamics model with an `ℓ_2`-norm multi-step prediction loss rather than ordinary mean-squared error, running TRPO as the inner policy optimizer against the learned model.

**Results.** On five continuous-control benchmarks from rllab (Swimmer, Half Cheetah, Humanoid, Ant, Walker), each with a maximum horizon of 500 steps (longer than most prior model-based RL benchmarks, which the paper notes makes the tasks harder), SLBO shows faster convergence (in number of real-environment samples) than SAC, plain TRPO, and a standard Model-Based TRPO baseline, while reaching better final performance using only 1 million real samples — matching or exceeding model-free TRPO's performance at 8 million samples using only 1 million. An ablation confirms the theory's own prediction: SLBO trained with the theoretically-motivated `ℓ_2`-norm loss significantly outperforms an otherwise-identical variant trained with the ordinary squared-`ℓ_2` (MSE) loss on four of the five environments.

**How it connects.** SLBO is the cleanest instance of this section's "improve a provable lower bound, not the raw model score" pattern, giving a rigorous foundation for exactly the model-based RL loop of §5 — and its lower-bound framework is a direct theoretical ancestor of MBPO immediately below, which the paper's own authors credit as building on a closely related discrepancy-bound idea.

### Paper Breakdown: MBPO (When to Trust Your Model)

*Citation: Michael Janner, Justin Fu, Marvin Zhang, Sergey Levine, "When to Trust Your Model: Model-Based Policy Optimization," NeurIPS 2019, arXiv:1906.08253.*

**Problem/motivation.** Model-based RL faces a basic tension: model-generated data is cheap and plentiful, but using too much of it (especially over long rollouts) risks compounding model error into a badly biased training signal — while using too little forfeits model-based RL's central sample-efficiency advantage. The question the title asks directly: exactly how much, and in what way, should a learned model actually be trusted during policy optimization?

**Key idea/innovation.** Rather than relying purely on full-length model rollouts (as SLBO effectively does), MBPO derives a monotonic-improvement bound (in the same theoretical family as SLBO's, "Theorem 4.1" in the paper) and then observes that the theoretical worst-case bound on model-induced error scales *quadratically* with the effective horizon `1/(1-γ)` — precisely because the theoretical bound has to account for a full-length rollout's worth of compounding model error, exactly Week 1's `T²ε` compounding-error argument (§3.2 of `week1-study-notes.md`) and this week's §5 multi-step-prediction discussion, appearing now for a **third time**, under yet another name: here it is "the discrepancy term in a model-based policy-improvement bound," in Week 1 it was "behavioral cloning's worst-case cost bound," and in §5 it was "why single-step dynamics training isn't enough." The fix MBPO derives directly from this observation: use **short, branched rollouts** — start a simulated rollout from a real state actually visited by a recent real policy, and run the (possibly imperfect) model forward for only a small number `k` of steps before stopping, rather than rolling the model out for the full task horizon.

**Method & training procedure.** MBPO combines three concrete pieces: an **ensemble** of probabilistic dynamics networks (directly reusing PETS' uncertainty-aware ensemble idea from §7), **short rollouts** of length `k` branched from states drawn from a buffer of real (not model-generated) past experience, and **Soft Actor-Critic (SAC)** as the policy-optimization algorithm consuming a mix of real and model-generated transitions. Concretely explaining *why* branching-and-truncating limits compounding error: a model trained on real, on-policy data is most accurate near the states that data actually covers; the *longer* a rollout continues purely inside the model without ever being corrected against a fresh real state, the further the simulated trajectory can drift from anywhere the model was actually trained on — exactly the same "policy's own errors carry it into never-seen states" mechanism as Week 1's covariate shift, just for a *dynamics model's own rollout* rather than a *policy's own rollout*. Starting fresh from a real state and stopping after only `k` steps caps how far this drift can accumulate before the next real anchor point resets it.

**Results.** On MuJoCo continuous-control benchmarks, MBPO learns "substantially faster, an order of magnitude faster on some tasks," than prior model-free methods while matching their asymptotic performance — concretely, MBPO's performance on the Ant task at 300,000 environment steps matches SAC's performance at 3,000,000 steps (a 10× sample-efficiency gain on that task specifically); on Hopper and Walker2d, MBPO reaches good performance using the equivalent of only 14 and 40 minutes (respectively) of real-time simulated interaction. Critically, MBPO scales successfully to higher-dimensional tasks like Ant, which the paper notes "pose problems for purely model-based approaches such as PETS" (§7 above) — directly crediting the short-branched-rollout design for this improved scaling. An ablation directly validates the theoretical motivation: fixing the rollout length at `k = 1` for the whole training run retains most of MBPO's benefit, `k` up to about 15 (following an increasing schedule) works best on Hopper specifically, and rollouts of length 500 are "too inaccurate for effective learning" — a direct empirical confirmation that longer, unbranched model rollouts really do compound error badly enough to hurt final performance, exactly as the theory predicts.

**How it connects.** MBPO is this week's third and clearest appearance of the compounding-error phenomenon first formalized in Week 1's BC bound (§3.2 of `week1-study-notes.md`) and echoed in §5's multi-step-prediction discussion — the branched-short-rollout fix is architecturally the model-based-RL analogue of DAgger's own fix for BC (Week 1, §4): both work by regularly re-anchoring against real, on-policy data rather than trusting a single long, uncorrected forward projection (a policy rollout in DAgger's case, a model rollout here).

### Value-aware model learning: a model that's accurate isn't automatically a model that's useful for control

Every model-fitting recipe described so far (§5's regression loss, PILCO's GP likelihood, PETS'/MBPO's ensemble likelihood) trains the dynamics model to minimize *state-prediction* error — how close is the predicted next state to the true next state, in an ordinary geometric sense. But the actual *goal* of a model-based RL system is not accurate state prediction for its own sake; it's *good control*. These two objectives can silently diverge: a model might predict most of the state extremely accurately while being badly wrong about exactly the one dimension, or one narrow region of state space, that the policy's decisions actually hinge on.

> **Weather-forecast analogy.** Imagine a weather model that predicts temperature, humidity, wind speed, and ten other variables with excellent accuracy everywhere — except it's badly wrong about wind speed specifically in the one mountain pass a hiker is deciding whether to cross today. For every purpose *except* that one decision, this is a great forecast; for the hiker's actual decision, it's useless, because the one variable and location that actually determines the right choice is exactly the one place the model fails. Ordinary prediction-error metrics (e.g. average error across all variables and locations) would still report this model as "highly accurate," completely missing that it's decision-relevant accuracy, not overall accuracy, that matters.

This is exactly the **objective mismatch** that motivates **value-aware model learning**: rather than fitting the model to minimize plain state-prediction error, fit it to minimize error specifically in the dimensions/regions of state space that actually affect the *value function* — i.e., that actually matter for the decisions a policy or planner would make.

### Paper Breakdown: VaGraM (Value-Gradient Weighted Model Loss)

*Citation: Claas A. Voelcker, Victor Liao, Animesh Garg, Amir-massoud Farahmand, "Value-Gradient Weighted Model-Based Reinforcement Learning," ICLR 2022, arXiv:2204.01464.*

**Problem/motivation.** Prior attempts at value-aware model learning (notably VAML and IterVAML, which directly penalize a model's error by how much it changes an estimated value function) tend to perform *worse* in practice than plain maximum-likelihood (MLE) model fitting, despite being better-motivated in theory — the paper diagnoses two concrete causes: these losses can depend on the value function evaluated at model predictions that land *outside* the region of state space the value function was ever trained on (where its outputs are meaningless), and their resulting loss landscape can have unstable, spurious local minima far from the true dynamics.

**Key idea/innovation.** **VaGraM** approximates the value-aware objective via a first-order **Taylor expansion** of the value function around the *actual observed* next state (rather than evaluating the value function at the model's own, possibly-far-off predicted next state) — this single change ensures the loss only ever depends on the value function at points actually in the training data, fixing the "evaluated outside its training region" failure mode above by construction. The resulting loss simplifies to weighting each *coordinate* of the ordinary squared prediction error by the squared **gradient of the value function** with respect to that coordinate: intuitively, `L_VaGraM ≈ Σ_i (∂V/∂x_i)² · (predicted next-state coordinate i − true next-state coordinate i)²` — a state dimension the value function barely depends on (small `∂V/∂x_i`) gets down-weighted in the model's loss, while a dimension the value function is highly sensitive to gets up-weighted, directly implementing the weather-forecast analogy's "focus modeling effort on what the decision actually needs" idea, using the value function's own gradient as the measure of "what the decision actually needs."

**Method & training procedure.** VaGraM is trained as a drop-in replacement for the ordinary MLE/MSE dynamics-model loss inside a standard model-based RL pipeline (structurally the same §5 loop, with only the model-fitting step's loss function changed), requiring only that a value-function estimate (already being computed by the RL algorithm's own critic) be available to compute its per-dimension gradient weights.

**Results.** On the standard MuJoCo benchmark suite, VaGraM matches ordinary MLE-based model learning when the dynamics network has ample capacity (both converge to similarly accurate models, since a sufficiently expressive network can fit the true dynamics well regardless of loss weighting). The gap opens up specifically in two challenging settings the paper highlights: with a **small dynamics model** (2–3 hidden layers, 64 units), VaGraM retains nearly its original performance on the Hopper task while the MLE baseline "quickly loses performance, completely failing to even stabilize the Hopper for a short period" in the smallest tested setting; and with **distracting state dimensions** (extra observation dimensions appended to Hopper that evolve under irrelevant, non-linear, discontinuous dynamics and have no effect on reward), VaGraM continues achieving reward comparable to the undistracted baseline (roughly 3200) with up to 15 distracting dimensions, while the MLE baseline's performance steadily deteriorates as more of its limited capacity gets wasted modeling the irrelevant dimensions; with 20 distracting dimensions, neither method could reliably stabilize the task any longer.

**How it connects.** VaGraM is this week's most direct, technically rigorous answer to the objective-mismatch problem the weather-forecast analogy above poses, and it closes out §8's throughline: SLBO and MBPO both ask "how do we know improving under the model improves the real system," while VaGraM asks the complementary question "how do we make sure the model itself is being trained on the right thing in the first place" — together, the two questions cover both halves of "trusting the model" named in this section's own title.

## 9. Synthesis — answering the four framing questions

### 9.1 Optimal control vs. learning-based methods

§0's comparison table (BC needs data and gives no guarantees; LQR needs a model and cost but gives a provable global optimum) was the first pass at this question; the machinery built since then fills in exactly *why* that table looks the way it does. LQR/iLQR's guarantees (§2.4, §3) come at the cost of needing an accurate model and hand-specified cost — both of which are hard to get right for a task as unstructured as, say, ALVINN's road-following (Week 1, §2) or Diffusion Policy's multimodal manipulation (Week 1, §7.4), where no one could plausibly write down a quadratic cost function capturing "drive safely." BC/DAgger's strength is exactly the opposite: no model or cost is ever specified, only demonstrated behavior — at the cost of the compounding-error problems Week 1 spent an entire section (§3–§4) formalizing and fixing.

| | Data requirements | Guarantees | Generality |
|---|---|---|---|
| Behavioral cloning (Week 1) | A dataset of expert demonstrations | None in general (Week 1 §3.2: `T²ε` worst case) | Handles whatever the data covers, however unstructured |
| DAgger (Week 1) | Demonstrations *plus* a live, queryable expert | Linear-in-`T` bound (Week 1 §4.3), given a no-regret learner | Same as BC, but needs an available expert during training |
| LQR / iLQR (this week) | Zero — no data, only a model and cost | Exact global optimum (LQR) or local optimum (iLQR) | Restricted to (locally) linearizable dynamics, quadratic-ish costs |
| Model-based RL (§5–§8) | Real-environment transitions to fit `f_θ` | As strong as SLBO's/MBPO's monotonic-improvement bounds (§8), when they apply | As general as the learned model's own coverage allows |

The two approaches are not just comparable, but genuinely **complementary**, in at least two concrete ways this week's material makes explicit: first, an MPC controller (§4) built from a known or learned model can itself serve as the live, queryable "expert" that DAgger (Week 1, §4.1) needs — MPC computes reasonable corrective actions from *any* state on demand, exactly DAgger's requirement, without needing a human in the loop at all. Second, a learned dynamics model (§5) is itself fit via perfectly ordinary supervised learning — the same regression setup as BC (Week 1 §2.2), just predicting next-state instead of expert-action — meaning model-based RL doesn't escape supervised learning's machinery so much as it *relocates* where that machinery is applied, from "predicting the action" to "predicting the consequence of an action."

### 9.2 Optimal control vs. world models

A world model (§5, and PlaNet concretely in §7) answers the question "what happens if I do this?" — it is a simulator, nothing more. On its own, a world model produces no actions at all; something still has to *decide* what hypothetical actions to simulate and *select* among them. That "something" is exactly the optimization machinery derived across §2–§3 (LQR/iLQR) and §6 (MPPI/CEM): a world model is **necessary but not sufficient** for control, and a planner is the missing piece that turns "I can predict the future" into "I know what to do right now." PlaNet's own architecture makes this division of labor unusually explicit: the RSSM (§7) is purely a simulator running in latent space, and CEM (§6) is bolted on afterward, unchanged from its derivation earlier in these notes, as the component that actually searches over hypothetical action sequences within that simulator. These are complementary pipeline components — a world model without a planner can't act, and a planner without a world model (or the real environment itself) has nothing to plan against.

### 9.3 Optimal control vs. neural networks

This week's material touches neural networks in three genuinely different roles, none of which pit "classical optimal control" against "neural networks" as competing alternatives:

1. **NN as the dynamics/world model** (§5, §7): PILCO's GP, the Gamboa Higuera et al. Bayesian NN, PETS' ensemble, DPI-Nets' graph network, DeepMPC's recurrent network, and PlaNet's RSSM are all instances of a neural (or GP) network standing in for the `f` that LQR/iLQR/MPPI/CEM all need as an input — the classical planning machinery doesn't change at all based on whether `f` came from a physics textbook or from gradient descent.
2. **NN made differentiable so gradient-based planning still works** (§6): the differentiable-physics Paper Breakdown's entire contribution is engineering a classical rigid-body simulator to expose the same kind of analytic gradients a neural network naturally has, specifically so that a classical gradient-based planner (iLQR) can run through it unmodified.
3. **NN inside a theoretically-grounded objective** (§8): SLBO, MBPO, and VaGraM all use a neural network as the dynamics model, but wrap its *training* in a provable bound or a value-aware weighting scheme, rather than treating "get a neural network to fit the data well" as sufficient on its own.

The throughline across all three: **optimal control is a computational scaffold that consumes neural-network-produced ingredients** (a predicted next state, a gradient, a value-function weighting) — it is not an alternative to neural networks competing for the same job, any more than a search algorithm competes with a heuristic function it happens to use.

### 9.4 Is classical optimal control obsolete, or still foundational?

Ben Recht's "Linearization Principle" (from his "Outsider's Tour of Reinforcement Learning" writeup, summarized below) offers a useful diagnostic here: understanding how a learning algorithm behaves on the *simplest* possible case — a linear system with quadratic cost, exactly LQR's assumptions — is not merely a toy exercise; behavior observed there (good or bad) tends to *persist* qualitatively once the same algorithm is scaled up to more complex, nonlinear settings. This is exactly why this week spent so much effort deriving LQR fully before ever touching a neural network: LQR is not a historical curiosity being superseded by deep model-based RL, it is the well-understood baseline case against which everything more complex is implicitly being checked.

The strongest evidence for optimal control's continued, load-bearing role sits in plain view across §6–§8's own Paper Breakdowns: **PETS' inner planner is CEM.** **PlaNet's inner planner is CEM.** **STORM's inner planner is MPPI.** **The differentiable-physics paper's inner planner is iLQR.** **DPI-Nets' control pipeline is gradient-based shooting plus MPC.** Not one of this week's celebrated modern deep model-based RL systems replaces the *decision-making* step with a bigger network — every one of them still uses a classical planning algorithm, derived from first principles in §2–§3 and §6, as its actual inner decision loop, applied on top of whatever new, learned world model the paper's own contribution improves.

The honest conclusion this week's evidence supports: classical optimal control is not a relic being phased out by deep learning — it is the **load-bearing planning layer** that most modern, neural-network-heavy model-based RL systems still sit on top of. What has changed dramatically is *what feeds into* that planning layer (learned, high-capacity, sometimes-latent world models instead of hand-derived physics equations); what has *not* changed nearly as much is the planning layer's own algorithmic core, whether that's a Riccati recursion, a softmin-weighted average of sampled rollouts, or an elite-refitted Gaussian.

### Reading write-up: Recht, "An Outsider's Tour of Reinforcement Learning"

*Citation: Benjamin Recht, "An Outsider's Tour of Reinforcement Learning" (blog series, argmin.net, 2018), and the companion tutorial paper "A Tour of Reinforcement Learning: The View from Continuous Control," arXiv:1806.09460 (Annual Review of Control, Robotics, and Autonomous Systems, 2019); ICML 2018 tutorial "From Learning to Control," people.eecs.berkeley.edu/~brecht/l2c-icml2018/.*

**What this reading derives/argues.** The blog series and its companion tutorial paper survey reinforcement learning explicitly through the lens of optimization and control theory, using the **Linear Quadratic Regulator with unknown dynamics** — i.e., exactly this week's LQR (§2), but with the dynamics matrices `A`, `B` themselves unknown and needing to be estimated from data — as the paper's central worked case study, on the grounds that it is "perhaps the simplest and best-studied problem in optimal control" and therefore an unusually clean setting for comparing what learning theory and control theory each have to say about the same underlying problem. The blog series' own table of contents moves through RL as "prescriptive analytics," RL as optimal control, a chapter explicitly on "the Linearization Principle," a chapter deriving LQR itself, and later chapters on policy-gradient methods and model-free approaches — mirroring, in blog form, almost exactly this week's own §1–§2 and §9 progression from Bellman/optimal-control foundations up through a direct comparison with model-free learning.

**Main takeaway/argument.** The tutorial's central argument is that "merging techniques from learning theory and control" yields sharper, more useful insight than either field's tools alone — specifically, it argues for taking seriously "the role and importance of models and the cost of generality in reinforcement learning algorithms": a fully general, model-free RL algorithm pays a real statistical and computational price for its generality, a price that classical control-theoretic analysis (of exactly the kind §2's LQR derivation makes fully explicit and provable) can make precise in the one setting simple enough to analyze completely.

**How it connects.** This reading is the direct source of framing question (4)'s "Linearization Principle" argument used in §9.4 above, and its own structural choice — build up rigorously from the fully-understood LQR case before saying anything about general nonlinear RL — is exactly the "start with the toy case" pedagogical move this week's own §2.1 makes for the identical reason.
